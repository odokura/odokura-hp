# XXGGLL セキュリティ

このカテゴリは、[セキュリティ基本設計](./basic-design.md)を実装可能な条件へ落とす正本である。基本設計で保護対象、脅威、信頼境界、Railway方針、管理体制、release gateを確認し、変更対象に対応する詳細だけを読む。

## 文書の責務

| 文書 | 決めること | 主な変更例 |
| --- | --- | --- |
| [セキュリティ基本設計](./basic-design.md) | 資産、脅威、信頼境界、統制構成、Railway、責任分界、公開gate | 基盤構成、管理体制、リスク判断 |
| [認証・認可・Ops](./identity-and-access.md) | 通常認証、セッション、再認証、Opsパスキー、登録・復旧、管理境界 | ログイン、設定、Ops API、管理者操作 |
| [データ・プライバシー](./data-and-privacy.md) | 収集制限、属性開示、匿名性、保持、削除 | プロフィール、Creator開示、VIP、退会 |
| [取引・不正・利用者安全](./transactions-and-safety.md) | 決済、台帳、Webhook、不正調査、コンテンツ安全 | 購入、返金、出金、通報、メッセージ |
| [監査・基盤・インシデント](./audit-platform-and-incident.md) | 監査対象、追記制約、シークレット、環境分離、初動 | 監査ログ、秘密値、調査、緊急停止 |

業務操作を確定できる条件は[コントロール](../core/controls.md)、保存構造は[データモデル](../core/data-model.md)、担当・頻度・証跡・復旧手順は[運用](../operations/operations.md)を正本とする。

## 変更目的から読む

| 変更目的 | 読む順序 |
| --- | --- |
| 通常ログイン・アカウント設定 | 認証・認可・Ops → データ・プライバシー → 要件・コントロール |
| Ops画面・管理API | 基本設計 → 認証・認可・Ops → 監査・基盤・インシデント → 運用 |
| プロフィール・属性・退会 | データ・プライバシー → データモデル → コントロール |
| 購入・返金・出金 | 取引・不正・利用者安全 → コントロール → データモデル |
| Railway・秘密値・障害対応 | 基本設計 → 監査・基盤・インシデント → 運用 |

## 共通前提

開発者、運用者、管理者は同一の一人で、通常の管理操作は一台の本人専用PCから行う。アプリケーションの有効な`ops_role='admin'`とRailwayの恒常的な人間用membershipは、それぞれ本人の一つだけを原則とする。

二人承認、職務分離、代替担当を設けない代わりに、固定target、PC外のpasskey・回復手段、再認証、原子的統制、監査、自動test、機能gateを省略しない。詳細と基本設計に差異がある場合は、実装者が一方を選ばず、変更Issueで両方を整合させる。

## 開発・供給網

- 実装リポジトリの依存関係は、コミット済みのlockfileを正本として再現可能なインストールを行う。
- push、Pull Requestおよび定期実行で、high以上の依存関係脆弱性監査と追跡済みテキストの秘密値検査を実行する。検査結果に秘密値、個人情報、決済詳細を出力しない。
- highまたはcriticalの脆弱性を例外扱いする場合は、対象パッケージ、影響範囲、理由、担当者、登録日、期限、次回確認日、対応方針をIssueまたは変更レビューに記録する。期限切れの例外は更新、代替または影響機能の停止を行う。
- GitHub Actionsの既定権限は`contents: read`に限定する。GitHubのSecret Scanning・Push Protectionなど外部リポジトリ機能を利用できない場合も、CIの秘密値検査を継続し、未達の外部条件を完了扱いにしない。
- 実装リポジトリにこの仕様の複製となるセキュリティ方針・保持方針・コンテンツ安全方針を作らず、必要な手順や検証結果からこの正本へリンクする。
