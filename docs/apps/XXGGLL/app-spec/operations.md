# XXGGLL 運用

## Issueと仕様照合

- XXGGLLのIssueは、作成時、着手時、実装変更時、完了判断時に[アプリ仕様](./overview.md)を入口として影響する正本仕様を確認する。
- Issue本文には、確認した正本仕様のGitHub URL、守る制約、変更する仕様、受け入れ条件を記録する。
- 実装と正本仕様に差異がある場合は、実装を正とせず、先に正本仕様を更新してIssue本文の確認内容も更新する。
- 完了前に、実装結果を要件の受け入れ条件と[コントロール仕様](./controls.md)に照合する。決済、出金、認可、属性開示、証票状態、監査に影響するIssueは、該当コントロールの失敗時・証跡・テストも確認する。
- Issue完了時の自動レビューは、仕様確認欄と`docs/apps/XXGGLL/`への参照がないIssueを失敗として記録する。
- 実装リポジトリのREADMEや補助資料は正本ではない。仕様・運用・セキュリティ・保持・公開判定の重複文書を実装リポジトリに置かず、必要な手順・検証結果・CI証跡だけを残して本正本へリンクする。

## Railway

- dev環境の標準リンク先はWebサービス`xxggll`とする。`xxggll-vip-dm-billing`はCron操作時だけ明示する。
- Railway CLIのkeyring認証と、Codex等の連携ツールのOAuth認証は別コンテキストである。一方の再認証で他方の
  認証状態を前提にしない。
- `railway whoami`と対象project/environment/serviceを指定した`railway status`が取得できれば、CLI認証は
  有効と判断する。`No service linked`や`not found in linked environment`は、認証失敗ではなく対象サービスまたは
  リンクの誤りとして切り分ける。
- ログ・ドメイン・変数を扱う操作では必ずserviceとenvironmentを指定し、変数値やcredentialファイルを表示・
  コピー・保存しない。

## 公開判定

- 機能を有効化する前に、[要件](./requirements.md)の該当機能ゲートを満たし、検証記録を残す。
- リリース候補では、型検査、単体テスト、統合テスト、migration確認、アクセシビリティ確認、秘密値検査、
  production buildを実行する。機能ごとに成功・失敗・Webhook・権限なし・再試行を確認する。
- 実行した環境名、コミットSHA、各結果、残る制約、ロールバック方法、Go/条件付きGo/No-Goを記録する。秘密値、
  決済詳細、利用者情報は記録しない。
- 異常時は該当機能をサーバー側の機能ゲートから外して再デプロイし、画面とAPIを利用不可へ戻す。既存の決済・
  台帳・監査ログを削除または上書きしない。

## 継続的なセキュリティ運用

- dev/mainへのpushと週次の定期実行で依存関係監査を行う。追跡済みテキストの秘密値検査は、値そのものをログへ出さない。
- GitHub Actionsの既定権限は`contents: read`に限定する。高・重大の依存関係例外は、対象パッケージ、影響範囲、
  理由、期限、担当者、更新確認日を記録し、期限切れ時は更新または機能停止を判断する。
- 秘密値の混入を検知した場合は、値を失効・再発行してから履歴の扱いを判断する。実際の形式に一致する秘密値を
  テストや例示に使わない。
- Stripe Webhookは署名検証、メール確認・パスワード再設定は一回限りの短期ハッシュ済みトークンを用いるため、
  CSRFの例外にできる。それ以外のブラウザ起点の更新APIはOrigin/Referer検証を必須とする。
