# XXGGLL 技術検証計画

実装前に、購入・保有・譲渡・VIP DMに利用者向け本人確認を要求しないこと、証票取得だけではクリエイター役務を
発生させないこと、カード情報・本人確認書類を自社保持しないことを、外部ベンダーと実装方式で確認する。

## V-1: Stripe Connectでの受領と出金の分離

- 買い手の支払いをSeparate Charges and Transfersで運営の残高へ集約し、出金申請時だけクリエイターへ送金できるか確認する。
- 出金申請中にConnected Accountを作成し、Stripeのホスト型オンボーディング（本人・事業者・口座確認、規約同意）へ遷移できるか確認する。
- `account.updated`等で送金可否を反映し、`payouts_enabled`相当になるまでTransferを実行しないことを確認する。
- カード情報・銀行口座情報・本人確認書類を自社インフラに通さずに決済・送金できるか確認する。
- 決済確定から90日後まで出金対象外にし、異議申立て・不正資料・公的要請時だけ最長180日保留できるか確認する。
- 返金時の台帳取消、二次流通の再発行クレジット、同一報酬への重複申請防止を確認する。
- 対応国は当面日本、通貨はJPYとする。将来の海外対応はStripeが有効と判定した国・通貨・経路だけを許可できるか確認する。
- 15分の在庫仮押さえに対応するオーソリ→キャプチャ方式を確認する。

**成功条件**: Stripe ConnectのSeparate Charges and Transfers、ホスト型オンボーディング、台帳・出金・返金の状態遷移を、
自社でカード情報・銀行口座情報・本人確認書類を保持せず実現できる。

## V-2: データ削除・環境分離

- 本番とテストの`DATABASE_URL`を分離し、`TEST_DATABASE_URL`は専用の使い捨てDBだけを指すことを確認する。
- 移行済みDBから旧本人確認テーブル、Profile照合状態、外部本人確認の参照値が削除されることを確認する。
- ログ、監査ログ、エラー応答、バックアップへ本人確認書類・生体情報・外部セッションIDが出力されないことを確認する。
- Stripe Webhookは署名検証と冪等処理を行い、本文を永続化しないことを確認する。

## V-3: 価格・発行数のルールベース算出

- 待機需要、価格感応度、過去の一次・継続・二次流通実績を入力とし、[価格・発行数の算出](../concept/general/pricing.md)の
  ルールを決定的な計算式で満たせるか確認する。
- 自己売買・関連当事者間取引を基準価格から除外できるか確認する。

**成功条件**: MLモデルや外部AIサービスを使わず、再現可能なルールベース計算で要件を満たせる。

## V-4: 一次発行・二次流通の在庫仮押さえのアトミック性

- `issuance_reservation`と`secondary_listing`の同時購入試行で、同一枠・同一証票が1件だけ成立することを確認する。
- 15分の期限切れと決済処理の競合を、単一DBのトランザクションで安全に処理できるか確認する。

**成功条件**: 負荷テストで常に1件だけ成立し、残りは競合エラーになる。

## V-5: クライアントのプラットフォーム選定

- 一般ユーザー・クリエイター向けをWeb単独で開始できるか確認する。
- MVPはWebで開始し、ネイティブアプリの要否は運用実績から判断する。

## 進め方とMVP着手ゲート

1. V-1（決済・報酬受取）を先に実機検証する。
2. V-2（データ削除・環境分離）をDB移行と同時に確認する。
3. V-4（在庫のアトミック性）をDBエンジン確定後すぐ検証する。
4. V-3（価格算出）は不成立ならクリエイター任意価格に絞る。
5. V-5はWeb単独で開始し、必要になったら後続フェーズで拡張する。

V-1またはV-4が不成立のままではMVPに進まない。本人確認が必要な対象は提供しないため、利用者向け本人確認ベンダーの
契約・検証はMVPの前提にもブロッカーにもならない。
