# XXGGLL 設計判断と未決事項

確定した実装レベルの設計判断と、構想から持ち越した未決の法務・技術確認事項を残す。業務ルールの判断理由は
構想側の各ページを正本とし、ここではアプリ仕様側の判断だけを記録する。

## 実装レベルの設計判断

| 判断 | 理由 |
| --- | --- |
| 小規模運用を前提に、単一の小さなアプリケーション（モノリス）として構築する。マイクロサービス分割はしない | 想定運用体制は少人数（場合によっては1人）。分散構成は運用負荷を増やすだけで、この規模では便益がない（→ [概要](./overview.md)「設計の芯」） |
| 運営ロールはMVPでは `admin` 1種類に集約する。役割ごとの専任コンソール・承認ワークフローは作らない | 実際の運営体制が少人数である以上、compliance/finance/trust&safety等に細分化しても実態が伴わない。`ops_role` をTEXTのまま拡張できる形にし、将来分割する余地だけ残す |
| 台帳は `ledger_transaction` + `ledger_split` の2テーブルではなく、`ledger_entry` 1テーブル（transaction_idで束ねる）にする | 按分の表現に必要十分な最小構成。ヘッダーテーブルを分ける複雑さは、この規模では不要 |
| 監査ログはハッシュチェーンを持たず、DB権限（UPDATE/DELETE不可）による追記専用で足りるとする | 改ざん検知基盤の構築・運用コストは、想定規模・想定脅威に見合わない。「まずはきちんとログを残す」ことを優先する |
| マネロン対策は、制裁対象者スクリーニング等の高度な仕組みを最初から作らず、台帳・KYC判定・状態遷移・運営操作の確実な記録を土台にする | 構想に資金決済の詳細な法務要件の記載がなく、実際の必要性も未確定の段階で高機能な監視基盤を先行投資する理由がない。必要になった時点で追加する |
| アカウント作成・証票の購入・保有・譲渡に年齢制限を設けない。全年齢向けサービスとする | 全年齢向けサービスとして想定されており、年齢確認は個別の対象コンテンツ・役務に法的必要性がある場合だけ行う条件付きKYCの枠組みで足りる |
| 対応言語は日本語のみとする | 小規模運用の想定規模では多言語基盤を持つ理由がなく、UI・法務レビューの範囲を広げない（2026-07-27改定。当初は3言語対応を検討していた） |
| KYC書類は自社DBに保存せず、KYCベンダーのホスト型フローに任せる | 本人確認書類を自社が保持しないことで、漏えい時の被害範囲とセキュリティ実装コストの両方を最小化する。これは「規模に応じた最小構成」とも両立する |
| カード情報・銀行口座情報は自社インフラを通過させない | 決済セキュリティの実装・監査コストを最小化する。既製の決済代行を使うことは、追加の作り込みを避ける選択でもある |
| 証票の来歴（certificate_event）は追記専用とする | 「証票来歴は改ざんされない」という利用者への信頼を、複雑な仕組みなしで実現できる最小限の設計 |
| secondary_listingに部分ユニークインデックスを設け、同一証票の同時出品を1件に制限する | 二重出品・二重成立という具体的な不正シナリオを、追加の監視サービスなしにDB制約だけで防げる |
| 重大操作（強制失効・プログラム終了確定・返金）はadminロールに限定し、監査ログに記録する。複数人承認は設けない | 少人数運用では複数人承認を必須にすると業務が止まる。記録を確実に残し、事後確認できる形を優先する |
| MVPのクライアントはWeb単独とし、ネイティブアプリ化は運用実績を見て判断する | 構想がクライアントの形態を指定しておらず、早期にプラットフォームを固定するリスクを避けるため |
| 価格・発行数の算出はMVPではルールベース（単純な計算式）で行う | 構想が要求する制約は単純な計算式でも表現でき、外部AIサービスや機械学習基盤を持ち込む必要がない |
| 証票支援は専用テーブルを新設せず、`ledger_entry`の新しいkind（`certificate_boost`）と、`certificate`への列追加（`boost_total_amount`）だけで実装する | 証票支援の本質は「按分記帳＋証票への匿名加算」であり、既存のledger_entry・certificateの仕組みにそのまま乗る。証票の行自体は譲渡でも変わらないため、boost_total_amountは追加ロジックなしに買い手へ引き継がれる |
| 決済通貨はUSD表記をデフォルトとする。`ledger_entry`・`service_engagement`・`payout_request`の`currency`既定値をUSDにする（2026-07-27改定。一時JPY・日本国内前提としていたが撤回） | 構想の[価格・発行数の算出](../concept/general/pricing.md)がもともと`$`表記であり、それをデフォルトとして踏襲する方針にした。ただし実際にUSD建て決済・JP在住クリエイターへの払出等をどう扱うかは、採用する決済代行（Stripe Connect）の仕様に依存するため、[技術検証計画](./tech-verification.md)のV-1で確認するまでは確定事項ではない |
| creator_profileはaccountと別ID空間のまま維持し、`owner_account_id`で明示的に紐づける（分離案） | クリエイターの運営上のアイデンティティを、本人が別途持ちうる一般ユーザーとしてのアカウントから切り離して扱えるようにするため。台帳（ledger_entry）のクリエイター分はcreator_id経由でcreator_profileへ解決し、再発行クレジット分だけparty_account_idに前保有者を記録する |
| 一次発行にも `issuance_reservation` を設け、15分の在庫仮押さえを `secondary_listing` のheldパターンと揃える | F-04・NF-02は一次・二次を区別せずに在庫仮押さえを要求しており、一次発行側にも同等の機構がなければ「最後の1枠への同時購入」を仕様どおりに扱えないため |
| 二次流通の基準価格計算のためだけに、同一決済手段・同一名義程度の安価な自己売買チェックを残す。専用の不正検知基盤は作らない | [価格・発行数の算出](../concept/general/pricing.md)の基準価格算出ルールが自己売買・関連当事者間取引の除外を前提にしており、検出を完全になくすとF-08・V-3が仕様どおりに実装できないため |
| attribute_share_consentにも部分ユニークインデックスを追加し、secondary_listingと同じ「同時に有効な行は1件」パターンに揃える | 片方のテーブルだけに制約があると、もう片方で同種のバグ（同意状態の重複）を見落としやすいため |
| certificate.rankにissuance_program.rankと同じCHECK制約を追加する | 参照先（issuance_program.rank）と重複する値を無防備に持たせないため |
| waitlist_entryにaccount_id（任意）を追加する | 構想がログイン済みアカウントでの待機登録を通知先登録と並ぶ選択肢として認めているため |
| ledger_entryにservice_engagement_id（任意）を追加する | S1/S2の支払い行から対象契約を直接たどれるようにするため |
| kyc_verification.target_refがポリモーフィックな参照（target_typeによって参照先テーブルが変わる）であることをコメントで明記する | DB制約で整合性を保証しない設計であることを、見落としではなく意図的な判断だと分かるようにするため |
| S1別商品に`s1_offering`（商品情報・数量上限）を新設し、`service_engagement`はそれを参照する個別の申込みとして扱う | 構想の任意提供・個別役務は、S1に「数量上限に達したら自動停止する」商品在庫の性質を求めているが、`service_engagement`単体（1契約1行）ではその在庫管理を表現できなかったため |
| 一次発行・継続支援・証票支援の売主・役務提供者・代金受領者は運営とし、クリエイターへの金員は別契約に基づくクリエイター報酬とする | 購入者の支払いを運営の売上受領として明確にし、クリエイターへの支払いを購入者からの預り金・送金や広告投稿の対価と混同しないため。購入価格・運営売上との配分率は約定せず、報酬額は取引ごとに算定する。広告投稿等を個別に委託する場合は、報酬とは別のプロモーション業務委託料として扱う |
| 二次流通は、運営が再発行価格を受領する再発行方式とする。前保有者へは価格の85%を再発行クレジットとして付与し、現金送金しない | 資金移動業の論点を避け、再発行クレジットを運営提供サービスだけに利用できる6か月失効の設計に限定するため。クリエイター報酬は取引ごとに別契約に基づき算定し、現金精算の対象とする |

## 現在の法務レビュー対象

決定済みの仕様を前提に、公開前または該当機能の公開前にだけ確認する事項を集約する。

| 論点 | 確認する範囲 | 実施時点 |
| --- | --- | --- |
| 条件付きKYC・個人情報 | 対象ごとの根拠、保存期間、削除・第三者提供、KYCベンダーへの越境移転 | KYCが必要な対象の公開前 |
| S1/S2・コンシェルジュ | 商品・役務ごとの提供条件、取消・返金、事故・知的財産権、記録の取扱い | 個別の商品・役務の公開前 |

一次購入を運営の売上受領、クリエイターへの分配を運営の支払債務とすること、二次流通を運営の再発行とすること、
前保有者へ現金送金・利用者間残高移転を行わないことは決定済みである。利用者への元本・利回り・収益分配・
買戻しを設けない限り、金融商品該当性は独立したレビュー対象にしない。

## 解決済みの論点（ユーザー確認 2026-07-27）

| 論点 | 結論 |
| --- | --- |
| 対応言語の範囲 | 日本語のみとする（当初は日英繁の3言語を検討していたが、2026-07-27に日本語のみへ変更） |
| 未成年者のアカウント作成・購入可否 | 年齢制限を設けない。全年齢向けサービスとする。個別の対象コンテンツ・役務に法的必要性がある場合だけ、条件付きKYCの枠組みで年齢確認を行う |
| マネロン対策の初期方針 | 高度なスクリーニング基盤を最初から作らず、台帳・KYC判定・状態遷移・運営操作を確実にログへ残すことを土台とする |
| 全体のシステム規模感 | 大規模なフィンテック基盤ではなく、小規模運用を前提にした最小構成で構築する（アーキテクチャ・データモデル・セキュリティの各ページへ反映済み） |
| クリエイター向け通知の方式 | 週次ダイジェスト（定期プッシュ配信）は行わず、ダッシュボードでの集計閲覧のみとする。クリエイターが開いたときに最新の集計を見られればよく、運営側に配信バッチを持つ理由がないため。構想の複数ページ・データモデルの`concierge_case.status`（`share_scheduled`→`share_reflected`）へ反映済み |
| 再発行クレジット | 運営提供の一次発行・再発行・継続支援だけに使える6か月失効クレジットとする。現金化・払戻し・チャージバック・他者移転は行わず、再発行の購入決済自体が取消された場合だけ対応する付与を取り消す |

## ベンダー選定（2026-07時点の調査結果）

各社サービスの比較調査と選定理由は[ベンダー選定](./vendor-selection.md)を正本とする。ここでは結論だけ記録する。

| 領域 | 第一候補 | 備考 |
| --- | --- | --- |
| 決済代行 | Stripe Connect（Separate Charges and Transfers） | 料金が唯一具体的に公開されており、クリエイターのオンボーディング審査をStripe側のホスト型フローに任せられるため、管理コストが最小になると判断した。購入と出金のタイミングを分離できる方式（→ 下の行）を実現するため、destination chargesではなくSeparate Charges and Transfersを選ぶ。C2C的マーケットプレイスに対するStripeのリスク審査は非公開のため、契約前に事業内容を事前説明する |
| 買い手の支払いは一旦運営のプラットフォーム残高へ集約し、クリエイターへの送金は`payout_request`による出金申請があったときだけ実行する（受領と出金の分離） | 購入のたびにクリエイター側のKYC・口座確認を求めるのではなく、何件かの購入で精算可能額が溜まってから、クリエイターが任意のタイミングでまとめて出金申請する運用にしたいというユーザー方針を反映した。通常のクリエイター報酬は決済確定日から90日後に精算可能とし、決済事業者・カード会社の異議申立て、不正利用を示す合理的な資料又は公的機関からの要請があるときだけ最長180日まで保留する。精算可能額として支払後の通常の返金・チャージバックは運営が負担し、クリエイターから回収しない。二次流通の前保有者には送金せず再発行クレジットを付与するため、Connected Accountを持つのはクリエイターだけで足りる。クリエイター報酬は運営の支払債務として記帳し、S1/S2の別契約対価・広告業務委託料・ライセンス対価とは区別する。海外クリエイターはStripeが有効と判定した国・通貨・送金経路のConnected Accountだけを利用でき、対象外の代替送金は行わない |
| KYC・年齢確認 | KYC不要のMVPでは未契約。KYCが必要な対象を公開する場合はDiditを第一実機検証候補とする | Diditはホスト型フロー、日本語UI、月額最低額なしの従量課金を公開しており、書類原本を自社運用で受け取るより小規模運用に適合する。ただしEU既定処理のため、対象ごとの法的根拠・越境移転、DPA/TOMs・再委託先、日本の対象書類対応、Webhook/削除の実機検証を採用ゲートとする。不成立時はTRUSTDOCK等の国内ベンダーを再比較する（→ [ベンダー選定](./vendor-selection.md)） |
| ホスティング/DB | Railway（アプリ本体 + マネージドPostgreSQL） | 単一モノリス構成と相性がよく、Git push一発デプロイ・マネージドバックアップで運用管理コストを抑えられる。Renderを次点として実装着手時に実機比較する |
