# XXGGLL ベンダー選定

本ページは、[技術検証計画](./tech-verification.md)のV-1（決済代行）・V-2（KYCベンダー）と、
[決定ログ](./decisions.md)で確定していなかったホスティング/DBの構成について、実在する各社サービスを
比較調査した結果と選定の正本である。想定運用規模は小規模であり（[概要](./overview.md)）、比較軸は
サービス費用に加えて**運用管理コスト**（審査・オンボーディングの手間、月々の運用作業）を重視する。

## 調査時点の注記

本ページの料金・仕様情報は2026年7月時点の公開情報（各社公式サイト・ドキュメント）に基づく。多くの
ベンダーが正式な単価を「要問い合わせ」としており、契約前に最新の見積もりを取得する必要がある。数値を
確認できなかった項目は「非公開」と明記し、憶測では埋めない。

### 選定: Stripe Connect（Separate Charges and Transfers）

**受け取りの流れ**

購入者ごと・取引ごとにクリエイターへ即時送金する方式（destination charges）ではなく、
[Separate Charges and Transfers](https://docs.stripe.com/connect/marketplace/tasks/accept-payment/separate-charges-and-transfers)
を採用する。買い手の支払いはいったんXXGGLL（運営）自身のStripeプラットフォーム残高へ入り、
[データモデル](./data-model.md)の`ledger_entry`で「誰にいくら払う義務が発生したか」を記帳するだけにとどめる。
クリエイターは、通常は決済確定日から90日を経たクリエイター報酬に対して任意のタイミングで`payout_request`により出金を申請し、
その時点で初めてStripeのConnected Accountを作成（未作成の場合）してTransferを実行する。二次流通の
前保有者にはTransferを行わず、再発行クレジットを付与する。
クリエイター側の本人・口座確認（Stripeのホスト型オンボーディング）も、この出金申請の中で発生する。これは、
利用者向けの条件付きKYCとは別の精算手続である。

**Connected Accountの運用範囲**

- Connected Accountはクリエイターの精算専用とし、購入者からの直接支払い、前保有者への送金、再発行クレジットの
  現金化には使わない。購入決済は常にXXGGLL（運営）名義で受領し、運営がmerchant of recordとなる。
- 初回出金申請で、クリエイターが認定する居住・事業国を`payout_country`として固定し、その国のConnected Accountを
  作成する。本人・事業者・口座情報とStripeのサービス契約への同意は、[Stripeホスト型オンボーディング](https://docs.stripe.com/connect/hosted-onboarding)で
  収集し、当社は保存しない。
- 国内・海外を問わず、出金はStripeが当該Connected Accountに対して`payouts_enabled`相当の送金可否を返し、
  かつ運営プラットフォームからその国・通貨への送金経路が有効な場合だけ実行する。Stripeの公式仕様では、
  Separate Charges and Transfersの通常の国境をまたぐ送金には地域制限があり、対象外の経路はエラーになる
  （[公式ドキュメント](https://docs.stripe.com/connect/separate-charges-and-transfers)）。海外クリエイターを一律に
  受け付ける設計にはしない。
- 計上通貨と実際の払出通貨が異なる場合、確定した送金額・通貨・換算レート・時点を出金申請に記録する。対象外の国、
  通貨または審査未完了に対して、銀行振込等の代替送金は行わない。

**理由**

- ユーザーの購入と、クリエイターへの実際の入金・KYCのタイミングを分離できる。何件かの購入で精算可能額が
  溜まってから、クリエイターが任意のタイミングでまとめて出金申請する運用にできる。
- 月額¥200の「有効な連結アカウント」課金は、Connected Accountが実際に入金を受けた月にだけ発生する。
  出金申請するまでConnected Account自体を作らないため、購入されただけでは1円もかからない。
- クリエイター（受取側）のオンボーディング・本人確認をStripeのホスト型フローに委ねられる。PAY.JPのマーケットプレイス型が要求する「テナントごとの個別審査」を運営側で持たずに済み、[概要](./overview.md)の「小規模運用を前提にする」方針に最も合う。
- 料金体系が唯一、月額¥200/送金ごと0.25%+¥250/決済3.6%という**具体的な数字で公開**されている。PAY.JP・KOMOJUはプラットフォーマー向け費用が非公開で、見積もりを取らないと総コストを比較できない。
- PaymentIntentsの2段階capture（オーソリ→キャプチャ）で、[データモデル](./data-model.md)の`issuance_reservation`／`secondary_listing`のheld状態が要求する「15分以内にキャプチャ or 解放」を無理なく実装できる。
- 決済通貨はUSD表記をデフォルトとする方針（[決定ログ](./decisions.md)）のため、JPY固定のKOMOJU・PAY.JPはこの時点で選択肢から外れる。Stripeが3候補中唯一USD建て決済に対応する。

**留意点（リスクとして記録）**

- StripeのC2C的なマーケットプレイスに対する審査は非公開かつ個別判断である。XXGGLLの二次流通は、運営が再発行価格を受領し、前保有者へ現金送金をせず再発行クレジットを付与する方式として、契約前にStripeサポート／営業へ事前説明する。
- Separate Charges and Transfersでは、購入代金がStripeのドキュメント上「XXGGLLが merchant of record（決済上の加盟店）」となる。返金・チャージバックはまずXXGGLL側の残高から引かれる（未送金分なら実害は小さい）。
- 買い手の支払いから実際のクリエイターへの送金までの間、Stripeのプラットフォーム残高に資金を長期間保持することについて、Stripe側の保持期間制限・リザーブ方針の明文化を今回確認できなかった。契約前にStripeへ直接確認する（→ [技術検証計画](./tech-verification.md)のV-1）。
- 決済手数料3.6%はPAY.JPのスタンダードプラン（3.3%）より高い。差分は「運営側の審査業務が発生しない」というオンボーディング側の管理コスト削減で相殺されると判断した。
- 「プラットフォーム管理モデル」（按分額を自社で指定する方式）を採用する前提。Stripeが提示する「Stripe管理モデル」（プラットフォーム手数料なし・Stripeが決済手数料を直接徴収）はパートナー条件付きのレベニューシェア契約であり、条件未確認のため今回の比較には含めていない。

### 追加候補: Didit

Passive Liveness・Face Match 1:1・Device & IP Analysisは各機能ごとに月500件まで無料で、その後は従量課金

### Diditを使う場合の最小実装

1. サーバー側で、対象コンテンツ・役務の法務承認済みKYC設定を確認して`kyc_verification`を`pending`で作成する。
2. サーバーだけがDiditのSessionを作成し、`vendor_data`には法的氏名等ではなくランダムなKYCレコードIDだけを渡す。
   セッションの`language`は`ja`に固定する。APIキーはクライアントへ配布しない。
3. 利用者をDiditホスト画面へ遷移させる。ブラウザからのreturn/callbackは完了表示にだけ使い、利用可否を確定しない。
4. Webhookの`X-Signature-V2`をサーバー側の秘密鍵で検証し、イベントIDまたはセッションIDで冪等に処理する。
   正常終了以外は対象の利用を許可しない。Webhook検証・結果反映・利用許可/拒否は監査ログへ残す。
5. 自社DBに残すのは目的、対象、`pass`/`fail`、判定日時、保持期限だけとする。DiditのセッションIDは削除APIの成功確認後に
   `vendor_reference_token`から消去し、書類画像、法的氏名、生年月日、抽出属性、Webhook本文は保存しない。
6. 最終結果の受信後、削除APIを自動実行する。失敗時は再試行キューに積み、成功するまで対象を「削除待ち」として
   運用画面に表示する。Didit側の通常保持期間も最短に設定する。

### 選定方針: KYCが必要になった時点の第一実機検証候補をDiditとする

KYCが不要なMVPでは、Diditを含めKYCベンダーを契約・呼び出ししない。KYCが必要な具体的コンテンツ・役務を
公開する場合は、後述する採用ゲートを満たせることを前提に、**Diditを自社目視確認より先に実機検証する第一候補**とする。
採用確定ではない。

**理由**

- [構想](../concept/foundation/concept.md)・[属性開示・条件付き本人確認](../concept/foundation/identity-disclosure.md)のとおり、KYCは「対象コンテンツ・役務単位で法的に必要な場合だけ」発動する設計であり、MVP時点でKYCが必要なコンテンツ・役務が実在するとは限らない。
- Diditはホスト型フローと従量課金を公開しており、書類の受領・閲覧・削除を自社運用するより、書類原本への接触範囲を小さくできる。
- 一方、Diditの既定処理地域はEUである。対象の法的根拠、越境移転、DPA/TOMs、再委託先、日本の本人確認書類の
  受理率、年齢判定の法的十分性は公開情報だけでは確定しない。
- アカウント作成・購入・保有・譲渡には年齢制限を設けない（[セキュリティ](./security.md)）ため、KYC運用の立ち上げはMVPのブロッカーにしない。

**採用ゲート**: (1) 対象ごとの確認根拠・必要な確認強度・保存期間を法務が承認する、(2) DiditからDPA/TOMs・
データ処理地域・再委託先・日本の対象書類/年齢確認の対応可否を取得する、(3) テスト環境で署名検証、再送、
重複Webhook、否認、削除失敗・再試行を確認する、(4) 本番想定件数で料金・再試行時課金を確認する、の4点とする。
満たせない場合は、国内データ処理・国内法令対応の実績を優先してTRUSTDOCK等を再比較する。自社で書類原本を
受け取る方式は、これらの選択肢がいずれも不成立の場合だけ検討する。

## ホスティング / DB

[決定ログ](./decisions.md)の未決事項だったDBエンジンの確定に合わせて、アプリ本体（単一のモノリス）と
PostgreSQLをどこで動かすかを比較した。

### 比較表

| 項目 | Railway | Render | Supabase | Fly.io |
| --- | --- | --- | --- | --- |
| 特徴 | アプリ+マネージドPostgresを1つのプロジェクトで完結。従量課金 | Herokuに近い体験。料金がプラン制で読みやすい | Postgres+Auth+Storageをまとめて提供するBaaS | マルチリージョンが主眼 |
| 目安料金（小規模） | Hobby月$5〜、実運用の目安は月$10〜15程度 | Web Service月$7〜、Postgres月$7〜（別課金） | 無料枠あり（DB 500MB・エグレス5GB）。本番はPro月$25〜 | 無料枠ありだが本番規模では従量課金 |
| マネージドDBとしての信頼性 | 自動バックアップ等マネージド運用込み | 自動バックアップ等マネージド運用込み | マネージド運用込み | 公式に「マネージドデータベースではない」と明言。障害復旧はユーザー責任 |
| 運用管理コスト | 低い（Git push一発デプロイ、DB作成もワンクリック） | 低い（同様にシンプル） | 低い。ただしAuth/Storageまで使うと独自の学習コストが発生 | Postgresの障害対応を自前で持つ必要があり、今回の「管理コストを抑えたい」方針に反する |

### 選定: Railway（アプリ本体 + マネージドPostgreSQL）

**理由**

- [アーキテクチャ](./architecture.md)で決めた「単一の小さなアプリケーション（モノリス）」構成と相性がよく、アプリとDBを同一プラットフォームでGit push一発デプロイできる。運用担当が少人数でも扱える。
- Fly Postgresは「マネージドデータベースではない」と公式に明言しており、障害復旧を自前で担う必要がある。これは[概要](./overview.md)の「規模に見合わない運用体制は持たない」方針に反するため除外した。
- SupabaseのAuth/Storageは魅力的だが、XXGGLLはすでに`account.ops_role`など独自のロール設計を持っており（[データモデル](./data-model.md)）、Supabase Authの仕組みに寄せ直すコストの方が大きいと判断した。将来、任意固定コンテンツ（R2）用のオブジェクトストレージが単体で必要になった場合は、Supabase Storageや他のオブジェクトストレージサービスを個別に検討する。
- RenderもRailwayと同等に有力。RailwayとRenderは同水準の運用管理コストであり、実装着手時に実機検証（デプロイのしやすさ、Postgresのバックアップ・リストア手順）で最終決定する。

## コスト試算（小規模想定）

創業初期の目安として、クリエイター数が少なく（有効な受取アカウント数件程度）、月間取引が少量の段階を想定する。

| 費目 | 概算 |
| --- | --- |
| Stripe Connect 固定費 | 月額¥200 ×その月に実際に出金申請したクリエイターの数（申請しなければ0円） |
| Stripe Connect 決済・送金手数料 | 決済額の3.6% + 送金（Transfer）ごとに0.25%+¥250 |
| ホスティング（Railway） | 月額 概算¥1,500〜3,000程度（$10〜20） |
| KYCベンダー | ¥0（KYC不要の間は未契約）。Diditを採用した場合は、公開単価・無料枠・再試行回数に応じた従量課金 |
| 監査ログ・改ざん検知基盤 | ¥0（[決定ログ](./decisions.md)のとおり自作しない方針） |

固定費はクリエイター数に比例するStripeの月額¥200と、ホスティングの月額数千円程度に抑えられる見込みで、
KYCベンダーの固定費（国内相場で月額¥30,000〜）を契約しない限り、小規模運用の間は月額1万円未満で
立ち上げられる見通しである。
