# XXGGLL コントロール仕様

コントロールは、業務ルールをサーバーまたはデータベースで強制し、失敗時に処理を止め、証跡を残す仕組みである。
画面でメニューを隠すこと、利用者に注意を表示することだけではコントロールにならない。

各コントロールは、対象、実行主体、強制箇所、失敗時の結果、証跡、テストで定義する。

## 決済

| ID | 守るもの | 強制箇所 | 失敗時 | 証跡・テスト |
| --- | --- | --- | --- |
| PAY-01 | 同じ購入要求を一度だけ決済・記帳する | `payment_attempt.idempotency_key` と `stripe_payment_intent_id` の一意制約。決済作成と台帳記帳は同じ購入要求を参照する | 既存の決済試行とその状態を返し、新規課金しない | 購入要求の再送、Webhook再送、途中失敗後の再開で台帳行と課金が各1回であること |
| PAY-02 | 1決済の台帳が一致する | `payment_attempt` と同じトランザクションで `ledger_entry` を記帳し、当事者別行の合計をサーバーで検証する | 不一致なら決済完了・台帳確定にしない | 決済試行ID、台帳行、検証結果 |
| PAY-03 | 返金は過去の行を書き換えない | 元の`payment_attempt`を参照する取消行だけを追記する | 元取引を特定できない返金を拒否する | 元決済ID、取消行、実行者、理由 |

## 出金

| ID | 守るもの | 強制箇所 | 失敗時 | 証跡・テスト |
| --- | --- | --- | --- |
| OUT-01 | 同じ報酬を二度出金しない | 出金作成時に対象`ledger_entry`をロックし、`payout_allocation`で台帳行の全額を予約する | 残高不足・競合時は申請を作成しない | 申請、予約した台帳行、予約額。並行出金で1件だけ成立すること |
| OUT-02 | 送金先と送金を一意にする | `payout_request.stripe_transfer_id`の一意制約。送金前にStripe recipient capabilityを確認する | `onboarding_required`または`failed`として記録し、代替送金しない | Stripe transfer ID、能力確認時刻、失敗理由 |
| OUT-03 | 返金の負担範囲を固定する | 精算前の取消しは予約額を減額する。送金済み報酬の通常返金は運営が負担する | 送金済み報酬をクリエイターから相殺・回収しない | 元決済、取消行、出金状態 |

## 認可と閲覧境界

| ID | 守るもの | 強制箇所 | 失敗時 | 証跡・テスト |

| AUTH-03 | Ops操作を登録済みパスキーを持つadminだけに限定する | Railway上の専用Ops Originで、完全一致の`OPS_ORIGIN`とそのホスト名に固定した`OPS_RP_ID`を本番起動時に検証する。5分以内・一回限り・開始ブラウザに結び付いたchallenge、WebAuthn署名、利用者検証、未失効credential、`account.ops_role='admin'`をサーバーで確認して、通常の`auth_session`と別の短期`admin_session`を発行する。通常セッションとメール・パスワード・X OAuth・メール再設定をOps認可へ流用しない | 設定不一致・非HTTPS・親ドメインRP ID・許可外Hostは起動またはプロキシで拒否する。未認証で到達可能なのは`/ops/sign-in`、事前認可済み`/ops/enroll`、監視専用`GET /ops/health`だけとする。healthは機密情報を返さずDB・外部serviceへ接続しない。その他の未認証ページ・旧`/admin`・`/api/admin`は、入力解析、構成確認、業務処理より先に理由を区別しない`404`とし、adminアカウント・credential・失効理由の存在を返さず、操作を確定しない。Opsセッションはアイドル15分・絶対8時間で失効する | 有効・未登録・失効済みパスキー、利用者検証なし、RP ID/Origin/challenge/署名不一致、challenge再利用・期限切れ、許可外Host、通常セッション・メール・パスワード・OAuthの拒否、`/ops/health`の最小応答、短期セッションの失効、認証成功・失敗・credential変更の監査 |
| AUTH-04 | Public個別リンクから対象や状態を列挙させない | 生トークンをSHA-256でハッシュして`public_entry_link.token_hash`と照合し、リンク・有料プログラム・クリエイターの公開条件を同時に検証する | 無効、取消、期限切れ、停止、非公開のすべてを同じ`404`にし、理由と対象IDを返さない | 有効・無効・期限切れ・停止・非公開・ランダム入力の応答が列挙を許さず、生トークンがDB・ログにないこと |
| AUTH-05 | 認証後の継続先を同じ許可対象に限定する | 継続先を同一Originの列挙済み相対ルートに正規化し、ログイン・登録・OAuth・メール確認の完了時にも再検証する | 不正・外部・未許可の継続先を破棄して`/home`へ戻し、外部リダイレクトしない | 同じ個別対象への復帰、外部URL、プロトコル相対URL、別対象、改ざん値の拒否テスト |
| AUTH-06 | Opsのユーザー画面確認を読み取り専用に限定する | AUTH-03のOpsセッションと`account.ops_role='admin'`を確認した専用read modelだけで、一人の対象ユーザーの表示情報を組み立てる。ユーザー本人のセッションやユーザー向け更新APIを使用しない | admin以外、不存在ID、失効したOpsセッションは同じ`404`とし、対象データを返さない。ユーザー操作を実行しない | 閲覧者admin、対象account、閲覧区画、時刻を監査する。パスキーadmin許可、通常セッション・一般利用者・対象外拒否、更新操作不在をテストする |
| AUTH-07 | OpsのCreator画面確認を読み取り専用に限定する | AUTH-03のOpsセッションと`account.ops_role='admin'`を確認した専用read modelだけで、一人の対象CreatorのCreator管理相当情報を組み立てる。Creator本人のセッション、管理権限、Creator向け更新APIを使用しない | admin以外、不存在ID、失効したOpsセッションは同じ`404`とし、対象データを返さない。Creator操作を実行しない | 閲覧者admin、対象Creator、閲覧区画、時刻を監査する。パスキーadmin許可、通常セッション・一般利用者・対象外拒否、個人ファン一覧・秘密値・更新操作不在をテストする |
| AUTH-08 | Opsクライアントへ本番DB資格情報を出さない | Railwayのサーバー処理だけへDB接続資格情報を設定し、Ops APIは有効なAUTH-03のOpsセッションを検証してからプライベートネットワーク経由でDBを利用する | ブラウザ、ローカル端末、パスキー認証器からのDB直接接続と公開DBエンドポイントを拒否する | Railwayの接続設定・DB公開状態をリリース前に確認し、クライアント応答・静的成果物・ログに資格情報がないことを検査する |
| AUTH-09 | 高リスクOps操作を直近のパスキー再認証に限定する | 返金、送金、強制失効、プログラム終了、既存adminのcredential追加・削除の確定直前に、`admin_session.reauthenticated_at`が5分以内であることをサーバーで確認する。再認証はAUTH-03と同じchallenge・RP ID・Origin・利用者検証の検証を通す | 通常セッションまたは5分を超えたOpsセッションは`reauthentication_required`として確定処理を実行しない。通常利用者のパスワード再認証を代替に使わない | 再認証challenge、成功・失敗・期限切れ、返金・送金・強制失効・プログラム終了・credential追加削除の許可・拒否、監査記録 |
| AUTH-10 | パスキー登録・削除をセッション窃取から守る | 初回・全喪失後の登録は、ローカルの`npm run ops:setup`が`railway whoami`を確認したうえで、固定した`dev` Project/Environment/Web serviceへ`railway ssh`で委譲した実行containerだけが発行する一回限りの登録記録、URLフラグメントの秘密値、開始ブラウザに束縛した5分以内の`__Host-`事前認可Cookie、WebAuthn登録challengeをすべて確認して確定する。初回bootstrapはactive accountが一件だけで有効credentialがない場合に限定し、recoverは旧credential、session、未完了登録、challengeを同一トランザクションで全て失効してから新しい登録記録を作成する。既存adminのcredential追加・削除は、5分以内の新しいパスキー再認証、adminロール、sessionとcredentialの失効状態を同一トランザクションで確認して確定する | 有効なOpsセッションだけ、通常ログイン、メール、ローカルDB接続、`railway run`、登録リンクの再利用、Cookieのみ、期限切れ、失効済みcredentialでは登録・削除を確定しない。ローカルcommandが固定対象以外へ接続する場合、active accountが複数の場合、登録link・Cookie・challengeの欠落と失敗理由は同じ`404`または安全な失敗として扱う | 初回登録、復旧、追加、削除、登録link・Cookie・challengeの再利用、期限切れ、セッション窃取を模した追加拒否、固定対象外・複数account・対話SSH以外の拒否、監査記録 |
| AUTH-11 | Ops失効を全要求へ即時反映する | 共通のOpsセッション検証が全Ops read/write要求でsession、credential、accountの現在の失効状態と期限を結合して確認する。credential失効またはadminロール解除は、該当session全件と未完了登録・challengeの失効と同一トランザクションで行い、adminロール解除はDBトリガーでも強制する。更新操作は認可確認から確定まで同じトランザクションでsessionとaccountをロックする | 失効または権限解除が先に確定したsessionは、画面・API・高リスク操作のいずれも`404`または再認証要求として確定しない。ロール再付与後も旧credentialと旧sessionを再利用できない | role解除・credential失効と並行したread/write、高リスク操作、全session失効、失効後とロール再付与後の再利用拒否をテストし、失効操作と結果を監査する |

## 監査・復旧

| ID | 守るもの | 強制箇所 | 失敗時 | 証跡・テスト |
| --- | --- | --- | --- |
| AUD-01 | 重大操作を証跡なしに確定しない | 決済確定、返金、出金、状態遷移、同意、権限付与、Ops操作を業務更新と同一トランザクションで監査記録する | 監査記録に失敗したら業務更新をロールバックする | `audit_log_entry`。操作ごとの必須項目テスト |

## 監査ログの必須内容

| 操作 | 必須記録 |

| 決済・返金 | 決済試行ID、対象、金額、通貨、結果、元取引、理由、実行者 |
| 出金 | 出金申請ID、予約台帳行、金額、Stripe送金ID、能力確認結果、状態 |
| 証票状態遷移 | 証票ID、変更前後の状態・保有者、理由、実行者 |

| 共有有効中のプロフィール項目更新 | 利用者、変更した許可キー名、各項目の共有状態、表示文面版、時刻、結果。入力値は記録しない |
| 現在保有者の個人開示閲覧 | Creator owner、Creator、発行プログラム、証票、対象アカウント、返却した項目の種別、時刻、結果 |
| 権限変更 | 対象クリエイター、スタッフ、権限、付与・撤回、実行者 |
| Opsパスキー | 確認済みadmin、credentialレコード参照、用途（認証・再認証・登録・失効・復旧）、結果、時刻、実行者または要求識別子 |
| Ops操作 | 対象、理由、利用者・クリエイターへの影響、結果、実行者 |
