# XXGGLL デザイン仕様

## 0. この文書の役割

この文書は、XXGGLLの全画面を同じ製品として体験できるように、画面の完成形、情報の優先順位、共通レイアウト、共通部品、状態、文言、レスポンシブ、受け入れ条件を定める正本である。

これは色や雰囲気だけを定めるブランドメモではない。利用者が各画面で何を理解し、何を判断し、次に何をできるべきかまでを決める。ページごとの好み、実装者の思いつき、既存画面の都合でこの文書を上書きしてはならない。

優先順位は次のとおりとする。

1. 法令、安全、権利保護、個人情報・決済の境界
2. [コントロール](./controls.md)
3. [要件](./requirements.md)
4. [UX](./ux.md)
5. [設定画面](./settings.md)
6. この文書
7. 個別画面の見た目の好み

## 1. デザインの目指す姿

XXGGLLは、利用者が自分の応援と保有の記録を落ち着いて確認し、Creatorは保有者全体の輪郭を理解し、運営は事実に基づいて対応できるサービスである。

画面の印象は「信頼できる記録帳」とする。派手なキャンペーンサイト、ゲームの報酬画面、SNSの反応画面、無機質な業務管理画面をページごとに混ぜない。

利用者が画面を移動したときに、次のことが自然に分かることを目指す。

- ここは何の画面か。
- いま何が起きているか。
- 自分に何が見えているか。
- 次に何をすればよいか。
- 操作すると何が変わるか。

### 1.1 完成画面の基準

- 初めて開いた画面でも、最初の表示領域でページ名、対象、現在状態が分かる。
- 主要操作がある場合、その操作は一つに絞られ、見つけるために画面全体を探し回らない。
- 情報量が多い画面でも、現在状態、要対応、次の操作、記録の順序が崩れない。
- 画面を移動しても、見出し、余白、ボタン、状態、一覧の見た目が同じ規則で動く。
- 利用者の期待を煽る装飾ではなく、記録、条件、期限、公開範囲を明確にすることで安心感を作る。

## 2. 全画面共通の原則

### D-01 関係の記録を中心にする

XXGGLLは、FanとCreatorの間に生まれた出来事を、取得・保有・表示できる一件の関係記録として扱う。発行No、取得日時、取得時のXフォロワー数、グッズ購入、支援履歴、現在状態、発行者への開示範囲は、対象となるXXGGLLに紐づけて表示する。

### D-02 一画面一目的にする

一つの画面には、利用者がその画面で完了させる目的を一つ置く。情報を追加できることと、操作を一つの画面へ詰め込むことを同義にしない。

Homeは現在状態、活動画面は振り返り、プロフィールは属性と開示、設定はアカウント管理、XXGGLL詳細は一件の状態と来歴を担当する。

### D-03 事実を装飾より先に出す

各画面は、次の順番で読む。

1. 対象
2. 現在状態
3. 重要な条件・金額・期限・数量
4. 利用者が次にできること
5. 履歴、境界、補足説明

見出し、説明、状態、操作、補足を同じ視覚強度にしない。利用者が判断に必要な事実を、装飾や長い説明の下へ隠さない。

### D-04 状態を事実として表示する

決済、Webhook反映、更新、返還、再発行、出金、返金、調査中を、「完了」「成功」の一語へ潰さない。表示する状態はサーバー側の状態値と対応させ、処理中・反映待ち・要対応・権限なしを別の状態として表す。

### D-05 公開範囲と役務の境界を見た目でも守る

アカウント名・出身国地域の自動開示、共通公開フラグによる任意プロフィールの開示、Publicへの公開を一つの「公開」ラベルへまとめない。XXGGLLの取得と、追加商品・VIP・ExtraVIPなどの別契約の役務を同じ特典カードへ混ぜない。

### D-06 人を移転・選別する見た目にしない

譲渡で引き継がれるのはXXGGLLの記録であり、前保有者の個人情報、支援額、属性、メッセージ、グッズ履歴ではない。Creatorの匿名集計を、支援者個人の一覧、営業リスト、選別画面に見せない。

### D-07 利用者にはXXGGLLと呼ぶ

利用者向けの見出し、本文、ナビ、ボタン、ラベル、代替テキストでは、XXGGLLを「証票」や「アーティファクト」と呼び換えない。`certificate`などの内部名はAPI、DB、技術対応表だけで使う。

### D-08 全画面を一つの製品として読む

Public、Home、Creator管理、Ops、Fanの詳細を、ページごとに別のサービスのようなレイアウトへ変えてはならない。差をつけてよいのは、ナビゲーションの表示範囲、情報密度、権限、Publicトップのヒーロー表現だけである。

ページ固有の背景、カード形状、見出し位置、ボタン体系、余白、アニメーションを新設する場合は、共通ルールで表現できない理由、対象画面、廃止条件を変更記録へ残す。

## 3. 共通ページフレーム

### 3.1 デスクトップの基本構造

1024px以上では、認証済み画面を次の一つのフレームで表示する。

```text
┌──────────────────┬──────────────────────────────────────┐
│ XXGGLL            │ ページ見出し                         │
│ シェル名          │ 説明・主要操作                       │
│                  ├──────────────────────────────────────┤
│ ホーム            │ 現在状態 / 要対応                     │
│ 保有XXGGLL        │                                      │
│ 活動の記録        │ 主対象の事実                          │
│                  │                                      │
│ アカウント        │ 履歴・補足・次の導線                  │
│ プロフィール      │                                      │
│ 設定              │                                      │
└──────────────────┴──────────────────────────────────────┘
```

- サイドバー幅は240pxで固定する。
- 本文フレームの最大幅は1180pxとし、画面中央に置く。
- 本文の左右余白はデスクトップで32px以上、上下のページ余白は32px以上とする。
- ページ見出し、本文、セクションの左端を揃える。カードだけを別の左端へずらさない。
- サイドバーを持つシェルは、Home、Creator管理、Opsで同じ幅・同じ現在位置表現を使う。

### 3.2 Publicの基本構造

Publicは上部ナビゲーションを使うが、本文幅、ページ見出し、セクション間隔、ボタン体系は認証済み画面と共通にする。Publicトップだけはヒーロー表現を許可し、`/flow`、`/fans`、`/creators`、`/pricing`、`/safety`は同じ説明ページの構造で作る。

Public下層ページを、ページごとに異なるランディングページへ変えてはならない。各ページは「ページ見出し → 結果の説明 → 代表UIまたは事実 → 次の導線」の順とする。

### 3.3 モバイルの基本構造

767px以下では、全画面で次を固定する。

- 共通モバイルヘッダー
- 一列の本文
- シェル専用の下部ナビゲーションまたは開閉式メニュー
- 44px以上のタップ領域
- ページ見出し、状態、主要操作、本文の順序

デスクトップで横並びだった内容は、重要度の高い順に縦積みする。左右に分けた情報を、横スクロールの奥へ隠さない。

## 4. レイアウトバリアント

ページのレイアウトは、次の四つから一つだけ選ぶ。ページごとの独自グリッド、独自カラム数、独自ヘッダーを作らない。

| バリアント | 対象画面 | 構造 | 利用者が感じる役割 |
| --- | --- | --- | --- |
| `reading` | Publicの説明・開始 | 見出し → 説明 → 代表UI → 境界 → 次の導線 | 仕組みを理解する |
| `workspace` | Home、活動、設定トップ、Creator概要 | 見出し → 現在状態 → 区画行・対象一覧 → 次の導線 | 自分の現在地を確認する |
| `detail` | XXGGLL詳細、プロフィール、設定詳細、確認画面 | 対象 → 状態 → 事実 → 主操作 → 来歴・補足 | 一つの対象を判断・変更する |
| `operation` | Opsキュー、ケース、監査 | 優先度 → 一覧 → 対象詳細 → 操作 → 監査 | 一件を安全に処理する |

`workspace`、`detail`、`operation`にPublicトップのヒーロー、斜めのカード、巨大な数値、装飾背景、ページ固有のフォントを持ち込まない。

### 4.1 認証後アプリの共通シェル

ログイン後のFan・Creator管理画面は、必ず`AuthenticatedAppShell`の一つの骨格で表示する。ページ固有のサイドバー、ページ固有のヘッダー、ページ固有の本文幅を作らない。差し替えるのは対象データ、見出し文、区画の有無、主要操作だけであり、画面の読み順は変えない。

```text
<AuthenticatedAppShell>
  <ShellNavigation />        共通ブランド、現在地、Home / 記録 / Creator / アカウント
  <Main>
    <ContextBar />            必要な場合だけ現在位置・対象
    <PageHeader />             h1、説明、主要操作
    <StatusRegion />           成功、エラー、利用制限、処理中
    <TemplateBody />           下記テンプレートの本文
    <PageFooterActions />      戻る、次の導線、確定後の導線
  </Main>
</AuthenticatedAppShell>
```

- デスクトップは240pxの共通サイドバー、モバイルは共通ヘッダーと下部ナビゲーションを使う。
- サイドバーのセクション名は`Home`、`あなたの記録`、`Creator`（権限がある場合だけ）、`アカウント`で固定する。`Studio`という独立した製品入口を設定やFanの導線に混ぜない。
- `ContextBar`、`StatusRegion`、`PageFooterActions`は不要なページでは省略できるが、残りの順序を変えない。
- アカウントメニュー、ログアウト、権限がないCreator導線、Ops導線をページ本文へ重複表示しない。
- 設定画面では、アカウントメニューの状態と本文のアカウント状態を同じサーバー確定値から表示する。

### 4.2 認証後画面テンプレート

各テンプレートは本文の骨格を固定する。情報量を増やすために新しいカード、タブ、サマリー帯をページごとに追加してはならない。

| ID | テンプレート | 固定する読み順 | 主な画面 | 禁止する混在 |
| --- | --- | --- | --- | --- |
| `T-Home` | 現在地・要対応 | PageHeader → 状態 → 主要対象 → 次の一手 | `/home`、Creator概要 | 活動グラフ、プロフィール編集、設定フォーム |
| `T-List` | 複数対象の確認 | PageHeader → 絞り込み・要約（必要時） → 一行一対象 → 空・ページング | 保有一覧、発行一覧 | 対象詳細の長いフォーム、別対象の情報 |
| `T-Detail` | 一件の判断 | PageHeader → 状態 → FactList → 主操作 → 来歴・補足 | XXGGLL詳細、設定確認 | 他対象の一覧、複数の確定操作 |
| `T-ViewEdit` | 閲覧から編集 | 完成ビュー → 編集操作 → 同じ項目順のFormSection → 保存・キャンセル | プロフィール、設定詳細 | 初期表示からのフォーム、編集項目の複製 |
| `T-Analytics` | 集計と振り返り | PageHeader → 最大4指標 → 区分・基準時点 → breakdown → 来歴 | 活動、Creator audience | 個人選別、他者順位、未確定値の合算 |
| `T-SettingsOverview` | 設定の現在地 | PageHeader → 状態 → 責務別の行 → 危険操作の境界 | `/fan/settings` | 長い資格情報フォーム、活動・保有・Creator機能 |
| `T-SettingsDetail` | 設定の変更 | PageHeader → 現在値 → 説明 → FormSection / ConfirmationPanel → 確定後状態 | `/fan/settings/security` | 異なる設定の同時編集、秘密値の表示 |
| `T-Operation` | 一件の安全な処理 | 優先度 → 状態 → 事実 → ConfirmationPanel → 監査 | Ops | Fan向け導線、ユーザー操作の代行 |

`T-SettingsOverview`の行は「項目名 → 現在値・状態 → 次にできること」の一形式にする。移動はリンク、変更・失効・ログアウトはボタンとし、設定トップで危険操作を主CTAにしない。

### 4.3 認証後画面のテンプレート割当

| ルート | テンプレート |
| --- | --- |
| `/home` | `T-Home` |
| `/fan/supports` | `T-List` |
| `/fan/supports/[id]` | `T-Detail` |
| `/fan/activity` | `T-Analytics` |
| `/fan/profile` | `T-ViewEdit` |
| `/fan/settings` | `T-SettingsOverview` |
| `/fan/settings/security` | `T-SettingsDetail` |
| `/studio/[creatorId]` | `T-Home` |
| `/studio/[creatorId]/offers/[id]` | `T-Detail`または`T-ViewEdit` |
| `/studio/[creatorId]/audience` | `T-Analytics` |
| `/ops`、`/ops/[...]` | `T-Operation` |

実装レビューでは、画面ごとにテンプレートIDを記録し、同じテンプレートの画面を並べて見出し、本文幅、行、状態、主要操作の位置が一致していることを確認する。

## 5. 共通ページヘッダー

### 5.1 ページヘッダーの完成形

```text
現在位置（必要な場合）
ページ名
この画面で分かることを1〜2文
                 [主要操作]
```

- ページ名は日本語の`h1`で一つだけ表示する。
- 説明文はページ名の言い換えではなく、利用者がこの画面で得る判断を述べる。
- 主要操作は右側または説明文の直下へ一つだけ置く。
- 戻るはページヘッダーの共通位置へ置き、本文の末尾に散らさない。
- 対象が一件ある場合は、ページ名の近くに対象名・識別子を表示する。
- 状態はページ名の代わりに色やバッジだけで表示しない。

### 5.2 見出し階層（D-23）

| 要素 | 役割 | 基準 |
| --- | --- | --- |
| `h1` | ページの目的 | 1画面に一つ。32px相当、行間1.2、モバイル28px相当 |
| `h2` | 主な区画 | 22px相当、行間1.4 |
| `h3` | 区画内の対象 | 17px相当、行間1.5 |
| 本文 | 判断に必要な説明 | 16px相当、行間1.75 |
| 補助文 | メタデータ・注意書き | 13px相当、行間1.6 |
| 識別子・時刻 | 発行No・日付・ID | `font-mono`または数値を揃えられる書体 |

見出しの英字、大文字、コード風の識別子を装飾として増やさない。日本語の見出しと英数字の行高・太さが大きく分断されない書体を使う。

## 6. 共通ビジュアルシステム

### 6.1 トークン

全シェルで次のトークンを共通語彙として使う。色値、余白、角丸、影、文字サイズをページCSSへ直書きしない。

| 種類 | 正本トークン | 基準値 |
| --- | --- | --- |
| 背景 | `--color-background` | `#f5f1e9` |
| 面 | `--color-surface` | `#fffdf8` |
| 補助面 | `--color-surface-muted` | `#e9e3d9` |
| 選択面 | `--color-surface-accent` | `#f2dfd3` |
| 本文 | `--color-text` | `#202a28` |
| 補助文 | `--color-muted` | `#68736f` |
| 境界 | `--color-border` / `--color-border-strong` | `#d8cfc2` / `#a9a097` |
| 操作 | `--color-accent` / `--color-accent-strong` | `#b04e32` / `#873b29` |
| 操作上の文字 | `--color-accent-contrast` | `#fffaf3` |
| 成功 | `--color-success` / `--color-success-surface` | `#2f6d4f` / `#edf6ef` |
| 注意 | `--color-warning` / `--color-warning-surface` | `#8a5a22` / `#fff7e8` |
| 危険 | `--color-danger` / `--color-danger-surface` | `#a0433a` / `#fff0ed` |
| フォーカス | `--color-focus` | `#1c5f8a` |

間隔は4px単位の`--space-1`〜`--space-6`を使う。ページの基本間隔は16px、区画間は24px、ページ上部・大区画間は32pxとする。新しい`19px`、`27px`のような任意値を画面ごとに作らない。

レイアウトの正本値は、本文最大1180px、説明本文最大760px、フォーム最大560px、サイドバー240px、操作最小44pxとする。

### 6.2 面・境界・カード（D-22）

- 基本は背景、境界線、余白で階層を作る。
- カードは一つの対象を開く、または一つの重要な状態を保持する場合だけ使う。
- 一覧、プロフィール項目、設定項目、監査項目をカードの連続として表示しない。境界線のある行を使う。
- カードを二重、三重に入れ子にしない。
- 標準の影は使わない。浮いて見える必要がある確認ダイアログやPublicトップの代表UIだけ、`shadow-sm`または`shadow-md`を使える。
- 角丸は入力・ボタンに`radius-sm`、標準面に`radius-md`を使う。丸みで情報の種類を表現しない。
- グラデーション、光彩、回転、グリッド背景はPublicトップのヒーロー区画以外では使わない。

### 6.3 色と状態（D-21）

- アクセント色は、主要操作、現在位置、関係記録をつなぐ構造に限定する。
- 成功、注意、危険、処理中、権限なしを同じ色で表示しない。
- 状態は色と、文字・形・アイコン・説明のいずれかを組み合わせる。
- ランク、人気、希少性、VIPを金属感、虹色、光彩だけで表現しない。
- Publicトップの`--world-*`色はヒーロー区画だけで使う。下層Public、Home、Fan、Creator管理、Ops、設定は共通`--color-*`を使う。

### D-20A Publicトップの表現モード

Publicトップのヒーローだけは、XXGGLLの記録性を伝えるために次の`--world-*`トークンを使える。他のPublic下層、Home、Fan、Creator管理、Ops、設定へ自動適用しない。

| トークン | 値 | 用途 |
| --- | --- | --- |
| `--world-background` | `#050806` | ヒーロー背景 |
| `--world-surface` | `#0a100c` | ヒーロー内の情報区画 |
| `--world-surface-raised` | `#111a13` | 代表XXGGLLの前面 |
| `--world-text` | `#f3f7ef` | ヒーロー見出し・本文 |
| `--world-muted` | `#a7b0a6` | ヒーロー補助文 |
| `--world-signal` | `#c9ff3d` | 主要操作、現在位置、記録の接続線 |
| `--world-cool` | `#5de0e6` | 奥行きを作る補助光だけ |

黄緑はブランドの信号色であり、成功、人気、希少、残数を意味しない。青緑は操作、リンク、状態の意味を持たせない。光彩とグリッドはヒーローの代表UIに集中させ、本文区画へ反復しない。forced colorsではブランド色と光彩を捨て、システム色で境界と操作を復元する。

## 7. 共通情報部品

同じ種類の情報を、画面ごとに違う部品へ変換しない。

| 部品 | 完成形 | 使う場所 |
| --- | --- | --- |
| `PageHeader` | ページ名、説明、対象、主要操作 | 全画面 |
| `StatusMessage` | 状態、原因、影響、期限、次の操作 | 注意、反映待ち、エラー、権限なし |
| `StatusBadge` | 短い状態名 | `StatusMessage`や一覧の補助 |
| `FactList` | ラベル、値、補助説明を縦に整列 | プロフィール、設定、詳細、金額 |
| `MetricGroup` | 2〜4個の重要指標を同じ基準で並べる | Home、活動、匿名集計 |
| `EntityList` | 一行一対象、識別情報、状態、次の操作 | 保有一覧、設定項目、Opsキュー |
| `EntityCard` | 対象、最重要事実、状態、単一操作 | Homeの現在対象、Publicの代表UI |
| `Timeline` | 日時、出来事、結果、補足 | XXGGLL来歴、活動記録、監査 |
| `FormSection` | ラベル、入力、説明、エラー、保存・取消 | 編集画面 |
| `ConfirmationPanel` | 対象、影響、再認証、確認文、確定・取消 | 購入、返還、削除、危険操作 |

### 7.1 指標のルール

- 指標は「意思決定に必要なもの」だけを置く。
- Homeの指標は現在保有数と要確認数を基本とし、累計金額や長期グラフを置かない。
- 活動画面では金額区分、月別推移、保有期間、ランク判定を同じカードへ混ぜない。
- 匿名集計では、人数、分布、期間推移を示し、個人の名前や識別子を混ぜない。
- 指標の数値を大きくすることを、画面の主役にしない。数値の意味、基準時刻、対象範囲を必ず添える。

### 7.2 一覧・表・行

- 一覧の一行は、識別情報 → 現在状態 → 次の操作の順とする。
- 行全体をリンクにする場合、操作ボタンを同じ行へ重ねない。
- 表はOpsなど比較が必要な場面だけに限定する。一般利用者向け一覧は原則として行形式にする。
- モバイルでは表をラベル・値の縦積み行へ変換し、主要操作を横スクロールの奥へ置かない。

### D-24 同じ情報は同じ視覚形式で出す

状態は`StatusMessage`または`StatusBadge`、属性と値は`FactList`、複数対象は`EntityList`、履歴は`Timeline`で表示する。同じ現在状態を、ページごとにピル、大きな色付きカード、本文中の一語へ変換してはならない。

金額、日付、発行No、件数は共通の整列規則で表示する。データの種類が同じなら、シェルが変わってもラベル、値、補助説明、状態の順序を変えない。

## 8. 操作と状態の設計

### 8.1 閲覧から編集への切り替え

プロフィール、設定、Creatorの設定など、利用者が値を確認してから変更する画面は、次の一貫した動きを使う。

```text
閲覧モード
  現在値、公開範囲、変更履歴、編集する

編集する
  閲覧時と同じ項目順のフォーム、説明、エラー
  保存する / キャンセル

保存後
  サーバー確定値、変更結果、次の導線
```

- 初期表示は閲覧モードとする。
- 編集ボタンはページヘッダー右側または対象区画の右上に置く。
- 編集時も項目の順序、ラベル、説明を変えない。
- キャンセル時は未保存変更を破棄する確認を必要に応じて表示する。
- 保存成功をクライアントの入力値だけで表示せず、サーバーの確定値を再表示する。
- 失敗時は編集前のサーバー状態を壊さず、失敗した項目の直下に原因と修正方法を表示する。

### 8.2 非同期状態

| 状態 | 表示するもの | 禁止するもの |
| --- | --- | --- |
| loading | 対象と読み込み中であること | 空データに見せる |
| empty | 空である理由と次の一手一つ | 空白だけを置く |
| processing | 操作対象、開始時刻、二重操作防止 | 無条件の再送 |
| pending | 何を待つか、再課金不要、再確認方法 | 完了・発行済みと表示 |
| success | サーバー確定結果、記録、次の導線 | HTTP成功だけで確定扱い |
| attention | 原因、影響、期限、復帰方法 | 赤色だけの警告 |
| unauthorized | 最小限の説明、ログイン・戻る | 対象の存在を推測させる詳細 |

画面下部に一時的なToastだけを出して重要な結果を伝えない。成功・失敗・反映待ちは対象の近くに持続表示する。

### 8.3 ボタンとリンク

| 種類 | 見た目 | 用途 |
| --- | --- | --- |
| Primary | アクセント背景、白系文字、48px | 画面の主要確定操作一つ |
| Secondary | 境界線、通常背景、44px | 主要操作の補助 |
| Tertiary | テキストリンク | 移動、補足、戻る |
| Danger | 危険色、確認領域内のみ | 削除、閉鎖、失効、返還など |

一つの画面にPrimaryを複数置かない。Dangerを通常のPrimaryと隣接させず、対象と影響を確認できる区画へ隔離する。

## 9. ページごとの完成形

### 9.1 Publicトップ `/`

利用者の問いは「XXGGLLは何が残るサービスか」である。

- 最初の表示領域は、価値の一文、短い説明、XXGGLLの代表UI、次に読む導線で構成する。
- 代表UIは実在の公開一覧に見せず、対象、状態、発行No、取得日時、期限、来歴の例を示す。
- Primaryは説明を読む導線、SecondaryはCreator開始またはログインとする。
- 料金、個人プロフィール、未実装の機能をファーストビューへ詰めない。
- ヒーロー表現はこのページだけに許可し、下層ページへコピーしない。

### 9.2 Public説明ページ `/flow` `/fans` `/creators` `/pricing` `/safety`

利用者の問いごとに一ページ一回答とする。

- `/flow`: 発行 → 取得 → 取得時点の記録 → 保有 → 振り返り → Creatorの匿名集計を一本の進行線で示す。
- `/fans`: 保有中のXXGGLL、来歴、活動記録、プロフィール共有、要対応を説明する。
- `/creators`: 発行管理と保有者全体の匿名統計を説明する。個人ファン一覧や接触機能と誤解させない。
- `/pricing`: Fanの支払、Creator報酬、精算、停止、返金を区別する。未確定の価格を購入可能に見せない。
- `/safety`: 認証、決済、プロフィール開示、前保有者情報、Ops境界を事実で説明する。

各ページは、ページ見出し → 得られる結果 → 利用できる機能 → 境界・注意 → 次の導線の順に固定する。機能カードを大量に並べず、代表UIは一ページにつき1〜2個にする。

### 9.3 認証と個別入口 `/sign-in` `/entry/[publicLinkId]`

- `/sign-in`の問いは「何のために認証し、完了後どこへ戻るか」である。ログイン・登録・X OAuth・パスワード再設定を一つの認証領域として見せる。
- `/entry/[publicLinkId]`の問いは「この対象を取得すると何が確定するか」である。対象、ランク、価格、残数、期限、継続・停止・返金条件を先に表示する。
- 確定操作は一つだけにし、認証後も同じ対象へ戻ることを表示する。
- 無効なリンクは対象や失効理由を推測させない共通の404状態にする。

### 9.4 Home `/home`

利用者の問いは「いま何を保有していて、何を確認すべきか」である。Homeは最初にアクセスする画面なので、説明文やナビゲーションの説明を本文へ重ねない。

```text
ホーム
現在の保有と、確認が必要なものを見られます

現在の状態       保有中 / 要確認
要対応           あれば一件ずつ原因・期限・操作
保有中のXXGGLL   現在状態、期限、次の操作
Creator管理      権限がある場合だけ発行管理への入口
```

- ファーストビューは現在状態と要対応を中心にする。
- 保有カードは一枚一XXGGLLとし、Creator、ランク、発行No、取得日時、状態、支払済み期限、次の操作を表示する。
- 活動グラフ、ランク判定の詳細、プロフィール編集、設定説明をHome本文へ置かない。
- 保有がない場合はFanの開始方法を一つだけ示し、Creator登録の勧誘を混ぜない。

### 9.5 保有XXGGLL `/fan/supports` `/fan/supports/[id]`

一覧の問いは「自分が持っているものは何か」、詳細の問いは「この一件は今どうなっていて、次に何ができるか」である。

- 一覧は一行一対象の`EntityList`。現在・過去・失効を別の世界へ分けず、状態ラベルで区別する。
- 詳細は対象と現在状態、取得時点、次の操作、連続した来歴、本人だけの支払・グッズ・応援記録の順とする。
- 自動継続の停止・再開、返還、再発行は対象詳細の状態に応じて一つずつ提示する。
- 前保有者の個人情報・支払内訳、他のXXGGLLの情報を表示しない。

### 9.6 活動の記録 `/fan/activity`

利用者の問いは「自分はいつ、何に、いくら関わり、どの状態へ反映されたか」である。

- 上部で「活動の記録」と「利用区分」を明確に分ける。
- Creator別の一次取得、継続支援、証票支援、確認済みグッズ、返金・取消し、保有期間を月別・来歴で表示する。
- 税・手数料・返金・取消し・再発行クレジットを別行・別区分で表示し、未確認額を合算しない。
- ユーザーランク、XXGGLLランク、Creatorランクを別の`FactList`として表示する。金額だけの進捗バー、他者順位、到達保証を表示しない。
- Homeへ戻る、対象詳細を開く、利用区分の説明を見る、の導線を末尾に置く。

### 9.7 プロフィール `/fan/profile`

利用者の問いは「自分のプロフィールはどう表示され、誰に何が開示されるか」である。

- 初期表示は完成したプロフィールビューとする。最初からフォームを表示しない。
- ヘッダー右側に`編集する`を置き、押すと同じ項目順の編集モードへ切り替える。
- 閲覧モードでは、基本情報、任意プロフィール、発行者への共有状態、現在の発行者、変更履歴を表示する。
- アカウント名・出身国地域の自動開示と、任意プロフィールの共通公開フラグを別の区画で説明する。
- 保存・キャンセルはフォーム末尾に置き、保存成功後はサーバー確定値へ戻す。

### 9.8 設定 `/fan/settings`

利用者の問いは「アカウント、ログイン、セッションをどう管理するか」である。

- 設定トップは認証済みアプリシェル上の`T-SettingsOverview`として、現在値と詳細画面への導線を表示する。
- アカウント、ログインとセキュリティ、アカウント操作、サポート・規約の順に固定する。
- パスワード、OAuthトークン、Cookie、決済カード、Opsパスキーを表示しない。
- プロフィール編集、活動記録、保有XXGGLL、Creator管理を設定へ複製しない。
- `contact`、`security`の詳細は`detail`として、対象設定の確認 → 編集 → 再認証 → 確定結果の順にする。
- アカウント閉鎖は最下部の危険領域に隔離し、保持・匿名化・保有中対象の条件が確定するまで完了操作を出さない。

### 9.9 Creator管理

Creatorの問いは「XXGGLLを正しく発行し、保有者全体の状態を活動判断に使えるか」である。Creator管理を別のブランドやSNSのようなStudioとして演出しない。

- 主な入口は`発行管理`と`保有者統計`の二つに絞る。
- 発行管理は、下書き・条件・公開状態・発行数・上限・要対応・一件の次操作を表示する。
- 保有者統計は、人数、ランク分布、地域分布、支援額帯、継続期間、グッズ傾向など匿名集計を表示する。
- 個人支援者一覧、匿名識別子検索、営業リスト、CSV出力を標準画面にしない。
- ownerだけが許可された発行プログラムの現在保有者について限定項目を読取できる。staffには返さない。
- 発行管理と保有者統計を一画面へ混ぜず、同じ共通フレームの別ページとして表示する。

### 9.10 Ops

Opsの問いは「何が要対応で、どの事実を確認し、どの操作を一度だけ実行するか」である。

- Opsは`operation`バリアントだが、共通のページヘッダー、状態表示、行、確認領域を使う。
- キューは対象、理由、優先度、期限、現在状態を比較できる一行形式とする。
- ケース詳細は対象 → 影響 → 根拠 → 操作 → 結果 → 監査の順とする。
- 返金、送金、強制失効、プログラム終了は、通常操作と離れた`ConfirmationPanel`で扱う。
- admin以外にはOpsの存在、管理対象、パスキー状態を表示しない。

## 10. ナビゲーションと導線

- DesktopのHomeサイドバーは、ホーム、あなたの記録、Creator管理、アカウントの順にする。
- アカウントにはプロフィールと設定だけを置く。活動や保有XXGGLLを設定の中へ隠さない。
- モバイル下部ナビゲーションは`ホーム | 保有XXGGLL | 活動の記録 | その他`の4項目を上限とする。
- `その他`にはプロフィール、設定、権限がある場合のCreator管理、サインアウトを置く。
- 現在位置は、文字・境界・背景の変化を組み合わせて示す。色だけで示さない。
- 画面本文でサイドナビゲーションの項目説明を繰り返さない。
- どの画面からも、戻る、現在位置、Homeへの帰路が分かるようにする。

## 11. 文言と情報密度

- 見出しは、利用者が答えを予測できる日本語にする。
- 「管理」「確認」「変更」「終了」など、操作の結果が分かる動詞を使う。
- 「設定」「詳細」「続ける」だけの曖昧なボタンを作らない。対象を含める。
- 補足説明は、対象、影響、期限、復帰方法のいずれかを伝える。
- 注意事項を画面下部の小さい文字に隠さない。
- エラーは「エラーが発生しました」で終わらず、原因、影響、復帰方法を表示する。
- 1つの区画に表示する主な数値は4つ以内とし、比較できない指標を同列に並べない。
- 長い説明は見出し・要約・詳細の三段階に分け、最初の表示領域に全文を詰め込まない。

## 12. レスポンシブとアクセシビリティ

- 1024px以上は240pxの共通サイドバーと1180px以内の本文を使う。
- 768px〜1023pxは本文一列を基本とし、補助区画を主対象の下へ移す。
- 767px以下は一列、共通モバイルヘッダー、シェル専用下部ナビゲーションを使う。
- 320px幅で主要操作を横スクロールなしに完了できる。
- 390px幅でページ名、説明、状態、主要操作が同じ順序で読める。
- 1440px幅で本文が1180pxを超えて拡散しない。
- 入力、ボタン、行の操作領域は44px以上とする。
- キーボードフォーカスを常に視認できるようにする。
- `main`、`h1`、フォームラベル、エラー要約、ライブリージョンを状態に応じて持つ。
- 色を無効にしても、状態、必須、選択、操作可能性を判断できる。
- `prefers-reduced-motion`とforced colorsを壊さない。
- 表はモバイルで行形式へ変換し、重要な操作やエラーを横スクロールの奥へ隠さない。

## 13. セキュリティ・プライバシーをデザインで補助する

見た目は認可の代わりにならないが、利用者が誤解しない境界を補助する。

- 未認証・権限なしの画面は、対象の存在、別利用者、admin権限、credentialの有無を推測させない。
- アカウント名・出身国地域の自動開示と、任意プロフィールの共通公開を別の説明・状態として表示する。
- Creatorの匿名集計を個人一覧へ見せない。
- 前保有者の個人情報・支援額・メッセージ・グッズ履歴を来歴の装飾として表示しない。
- パスワード、OAuthトークン、Cookie、決済カード、銀行口座、DB接続資格情報、Opsパスキー秘密情報を画面へ出さない。
- 支払い、返金、送金、失効、アカウント閉鎖は対象、影響、確認、確定結果を確認領域へまとめる。

## 14. 実装・レビューの契約

画面を実装または変更する前に、次を変更記録へ書く。空欄を既存コードから推測して埋めない。

| 項目 | 記録内容 |
| --- | --- |
| 対象 | 何を表示・操作する画面か |
| 利用者 | Fan、Creator、staff、admin、未認証者 |
| 最初の問い | 利用者が最初に答えたい問い |
| 最重要の事実 | ファーストビューで見せる対象、状態、条件 |
| レイアウト | `reading`、`workspace`、`detail`、`operation`のいずれか一つ |
| テンプレート | `T-Home`、`T-List`、`T-Detail`、`T-ViewEdit`、`T-Analytics`、`T-SettingsOverview`、`T-SettingsDetail`、`T-Operation`のいずれか |
| 共通部品 | PageHeader、StatusMessage、FactList等の使用箇所 |
| 主要操作 | 一つの主操作、確定条件、失敗・再試行 |
| 見せないもの | 権限外、秘密値、誤認させる情報 |
| 状態 | loading、empty、processing、pending、success、attention、unauthorized |
| 実画面証拠 | 1440px、390px、320pxと対象ロール・状態 |

### 14.1 受け入れ条件

- 共通フレーム、ページヘッダー、見出し階層、本文幅、主要操作位置が全画面で揃っている。
- 認証後画面にテンプレートIDが割り当てられ、同一テンプレートの画面で骨格・行・状態・主要操作の位置が揃っている。
- 代表する`reading`、`workspace`、`detail`、`operation`を並べたとき、別製品に見える固有レイアウトがない。
- 同じ状態、金額、日付、履歴が同じ共通部品と順序で表示される。
- 各ページの最初の表示領域に、ページ名、対象、現在状態、次の操作がある。
- 閲覧から編集への切り替えは、プロフィール・設定・その他の編集画面で同じ動きをする。
- 320px、390px、1440pxで、折返し、余白、ナビ、主要操作、エラー、空状態を確認している。
- 色、影、角丸、フォント、背景、グリッドをページ単位で勝手に追加していない。
- 公開範囲、個人情報、役務、決済、Ops境界の仕様と画面表現が一致している。
- 単独の画面がきれいなだけでは合格とせず、画面横断の比較レビューを完了している。

機械検査、実画面検査、独立レビューを混同しない。実画面を確認していない状態は`NOT VERIFIED`であり、合格としない。
