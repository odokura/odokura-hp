# XXGGLL デザインルール

## 0. この文書の役割

この文書は、LLMがXXGGLLの画面・コンポーネント・文言・スタイルを変更するときに、
何を守り、何をコードで確認し、何をブラウザで確認し、何を合格と呼べるかを定義する。

これは雰囲気を共有するためのブランドメモではない。実装、自己レビュー、独立レビュー、
修正判断、例外記録に使うデザイン契約である。

この文書単独で、権限、決済、属性開示、状態遷移、監査、役務の境界を変更してはならない。
優先順位は次のとおりとする。

1. 法令、安全、権利保護
2. [コントロール](./controls.md)
3. [要件](./requirements.md)
4. [UX](./ux.md)
5. [XXGGLLコンセプト](../concept/foundation/concept.md)
6. この文書
7. 個別の画面上の都合、LLMの推測、見た目の好み

## 1. ルールの読み方

| 表記 | 意味 | 証拠なしの扱い |
| --- | --- | --- |
| MUST | 実装・レビューで必須 | 合格不可 |
| MUST NOT | してはならない | 検出時は不合格 |
| SHOULD | 原則として守る | 例外理由が必要 |
| MAY | 条件を満たす場合だけ任意 | 判断理由を記録 |

LLMは、文章を読んで「守ったはず」と判断してはならない。各MUST/MUST NOTについて、
コード、コマンド出力、ブラウザ画面、またはレビュー記録のどれが証拠になるかを示す。
証拠を作れないルールは、ルールの不足として扱い、合格条件にしない。

この文書の`D-xx`ルールは、本文に`SHOULD`または`MAY`と書かれていない限り`MUST`として扱う。

## 2. デザインの不変条件

次の不変条件は、色やレイアウトより優先する。

### D-01 関係の記録である

XXGGLLは、ファンとクリエイターの間に生まれた出来事を、取得・保有・表示できる一件の関係記録へまとめる。
画面はこの価値を、発行No、取得日時、取得時のXフォロワー数、グッズ購入、支援履歴、現在状態、同意の範囲として表示する。

### D-02 役務を暗示しない

XXGGLLの取得だけで、個別の返信、制作、配信、物品提供、接客、面会が発生するように見せない。
追加商品、VIP、ExtraVIP、個別契約の役務は、XXGGLLと別の契約・決済・状態として表示する。

### D-03 人を移転しない

XXGGLLの発行Noや公開来歴を表示しても、前保有者の氏名、支援額、グッズ購入履歴、属性、メッセージ、退出理由を表示しない。
譲渡を「関係を引き継ぐ」「前保有者の情報を取得する」と誤認させない。

### D-04 同意を接触権にしない

属性開示は項目単位、対象単位、同意状態単位で表示する。開示されたことを、閲覧、返信、面会、
承認、選別の権利として表現しない。

### D-05 状態を事実として表示する

決済、Webhook反映、更新、返還、再発行、出金、返金、調査中の状態を、成功・完了・承認の一語に潰さない。
利用者が今できる操作と、まだできない操作を状態に合わせて表示する。

### D-06 公開範囲を増やさない

Publicに、公開カタログ、検索、カテゴリ、クリエイター一覧、関連提供物、無料コンテンツ一覧を置かない。
個別リンクの対象限定表示を、カード、関連リンク、検索、サイトマップで類推可能にしない。

### D-07 利用者にはXXGGLLと呼ぶ

利用者向けの見出し、本文、ナビ、ボタン、ラベル、代替テキストでは、XXGGLLを「証票」や
「アーティファクト」と呼び換えない。`certificate`等の内部名は、API、DB、技術対応表だけで使う。

## 3. LLMが実装する画面の契約

LLMは、コードを書く前に次の5項目を変更記録へ書く。記録がない画面変更はレビュー対象にしない。

1. 対象シェル: Public、Home、Studio、Opsのいずれか
2. 対象ロールと閲覧境界: 誰に見えるか、誰には存在も見せないか
3. 画面の主対象: XXGGLL、プログラム、提供物、支援履歴、属性、決済、監査など
4. 状態表: loading、empty、processing、pending、success、attention、unauthorizedの表示と操作
5. 主要操作: 何を確定するか、確定前に何を見せるか、失敗・再試行・二重送信をどう扱うか

LLMは、上記を決められない場合に実装を始めてはならない。コードから都合よく仕様を推測し、
正本仕様を上書きしてはならない。

## 4. 情報階層のルール

### D-10 一画面一目的

画面の最上部で、対象、現在状態、主要操作が分かるようにする。見出し、説明、状態、操作、補足を
同じ視覚強度にしない。

### D-11 事実を先に出す

決済や関係記録に関わる画面では、装飾より次の順序を優先する。

1. 何の対象か
2. 現在どうなっているか
3. 金額・期限・残数・条件
4. 利用者が次にできること
5. 補足、法的説明、関連リンク

### D-12 主要操作を競合させない

一つの画面・カード・確認領域に、同じ強さの主要ボタンを複数置かない。危険操作は通常操作と分離し、
対象と結果を具体的に確認してから一度だけ実行する。

### D-13 表現をデータと一致させる

「完了」「有効」「公開」「承認済み」「保有中」などのラベルは、サーバー側の状態値と対応させる。
クライアントの一時状態、決済成功画面、HTTP成功だけを根拠に確定状態を表示しない。

## 5. シェル別ルール

### Public

- トップでは、Fanの応援が振り返れることと、Creatorがファン全体の輪郭を活動判断に使えることを先に約束し、発行No、取得日時、取得時のXフォロワー数、グッズ購入を持つ大きなXXGGLLをその根拠として示す。データ項目や抽象的な世界観説明を価値命題より先行させない。
- 主ナビは`XXGGLLの流れ`、`ファンに残るもの`、`クリエイターに分かること`、`安全性`、`ログイン`または`ホームへ`で構成し、すべてのPublicページから`/flow`へ1クリックで進めるようにする。内部概念を英語で並べず、リンク先で答える問いが予測できる文言にする。
- `/flow`は、発行からCreatorの次の判断までを一本の進行線と7段階で示す。各段階は結果を述べる見出し、二文以内の説明、代表UI一つに限定し、小カードの一覧や横向きの巨大フロー図にしない。
- `/fans`と`/creators`は、利益の説明に続けて、現在利用できる機能を独立したセクションで説明する。各機能は`使う場所`、`見えるもの`、`次にできること`を示し、将来機能や未実装の操作を現在利用できるものとして記載しない。
- `/fans`の機能説明は、保有中のXXGGLL一覧、一枚の詳細と連続した来歴、共有する相手と項目の選択・撤回、現在状態と要対応の確認を扱う。
- `/creators`の機能説明は、XXGGLLの下書き・設定・公開、発行状況の一件単位の管理、個人一覧ではない匿名集計、収益・精算状態の確認と申請を扱う。
- Fanは個別リンクから直接始めるため汎用のFan取得操作を作らず、Creatorには`XXGGLLを発行する`を示す。
- 個別リンクでは対象、価格、残数、取得条件、役務が発生しないことを明示する。
- 一覧性を作るUIを追加しない。`map`による公開カード一覧、検索入力、カテゴリナビゲーション、関連商品導線を追加しない。
- ログイン後に元の対象へ戻れることを表示する。
- 認証・権限エラーは、対象の存在や別利用者の情報を推測させない。

### Home

- FanとCreatorを別アプリのように分断せず、共通ホーム内で権限に応じたカードを表示する。
- Fanカードは、クリエイター、ランク、発行No、取得日時、状態、支払済み期限、次の操作を示す。
- Creatorカードは、ランク、公開状態、発行数・上限、要対応、匿名集計を示す。
- 現在・過去・失効・譲渡・終了を、別の記録として切断せず、XXGGLLの連続した来歴として示す。

### Studio

- URLの`creatorId`だけで対象を決めず、セッションがownerまたは許可済みstaffとして管理できるCreatorだけを表示する。
- 個人の連絡先、決済情報、未同意プロフィールを返す・想像させるカードを置かない。
- 匿名集計を、個人選別、承認、営業、接触のための一覧に見せない。
- 収益、保留、精算申請、送金状態を、対象取引と状態に分ける。

### Ops

- 管理者専用とし、非管理者にはメニューだけでなく対象の存在も見せない。
- 返金、失効、停止、出金、通報対応は、対象、理由、影響、結果、監査記録を確認できる形にする。
- 利用者向けの安心感を演出するのではなく、誤操作と監査不能を防ぐ情報密度を優先する。

## 6. ビジュアルルール

### D-20 トークン経由で表現する

新しい色、間隔、角丸、影、文字サイズをコンポーネントへ直接記述しない。意味を持つトークンを経由する。
最低限、次の役割を持つ。

- 色: `background`、`surface`、`text`、`muted`、`border`、`accent`、`success`、`warning`、`danger`、`focus`
- 間隔: `space-1`から`space-6`
- 形状: `radius-sm`、`radius-md`、`radius-lg`
- 文字: `font-body`、`font-heading`、`font-mono`、本文・補助・見出しのサイズ
- 効果: `shadow-none`、`shadow-sm`、`shadow-md`、モーション速度、フォーカスリング

実装リポジトリの既存表現名トークンは、移行完了まではレガシーとみなす。新規コードで、
色値の直書き、`--cyan`のような色相依存名、画面固有の影を増やさない。

### D-20A Publicトップのブランド色

Publicトップは次の専用トークンを正本とする。他のシェルへ自動適用せず、色値をコンポーネントへ直書きしない。

| トークン | 値 | 用途 |
| --- | --- | --- |
| `--world-background` | `#050806` | ページ背景 |
| `--world-surface` | `#0a100c` | 情報区画 |
| `--world-surface-raised` | `#111a13` | 前面のXXGGLL表示 |
| `--world-text` | `#f3f7ef` | 見出しと主要本文 |
| `--world-muted` | `#a7b0a6` | 補足とメタデータ |
| `--world-signal` | `#c9ff3d` | 主要操作、現在位置、記録の接続線 |
| `--world-cool` | `#5de0e6` | 奥行きを作る補助光だけ |

- 黄緑はブランドの信号色であり、成功、人気、希少、残数を意味しない。
- 青緑は操作、リンク、状態の意味を持たせず、ヒーローの補助光に限定する。
- 光彩とグリッドはヒーローのXXGGLL表示に集中させ、本文区画へ反復しない。
- `forced-colors`ではブランド色と光彩を捨て、システム色で境界と操作を復元する。

### D-21 色は状態・階層に限定する

- アクセント色は、一画面の主要操作、現在位置、関係記録をつなぐ構造ラベルに限定する。
- 成功、注意、エラー、処理中、権限なしを同じ色で表さない。
- 色、光彩、金属感、虹色だけでランク、VIP、希少性、人気を表さない。
- 状態は文字、形、アイコン、説明の少なくとも一つを色と併用する。
- コントラストとフォーカス表示は、デザインレビューではなくアクセシビリティ検査でも確認する。

### D-22 形と効果は情報を邪魔しない

- カードは情報のまとまりを示す場合だけ使う。
- 状態ラベルのピル形を、すべての要素へ広げない。
- グラデーション、グリッド背景、光彩、強い影、ホバー浮上は標準表現にしない。
- 画像がなくても対象、状態、条件、主要操作を理解できるようにする。
- 私的な顔、生活空間、接触を想起させる素材を、権利・公開範囲の確認なしに使わない。

### D-23 文字と数値を読むために設計する

- 日本語を本文の基準言語とする。
- 見出し、本文、補助、状態、数値の役割を分ける。
- 金額、日付、XXGGLLの発行No、残数、支払済み期限を比較しやすく整列する。
- 見出しの英語、略語、演出用コード、意味のない大文字表現を増やさない。
- 注意事項を小さくして隠さない。

Publicトップの英字は小さな識別ラベルに限定する。ナビ、見出し、操作は、来訪者が意味と遷移先を
予測できる日本語を使う。装飾だけの英字列で本文の日本語を置き換えない。

## 7. コンポーネント契約

新規コンポーネントは、見た目ではなく契約で追加する。実装前に次を記録する。

| 項目 | 必須内容 |
| --- | --- |
| 目的 | 既存部品で解決できない理由 |
| 入力 | 表示対象、状態、ロール、操作、文言 |
| 出力 | 画面表示、イベント、遷移、監査対象 |
| 禁止 | 権限漏れ、二重操作、誤認を起こす使い方 |
| 検証 | 静的検査、アクセシビリティ、状態、画面幅、エラー経路 |

最低限の共有部品は、必要になった時点で次の契約を持つ。

- `PageHeader`: ページ名、対象、状態、主要操作
- `StatusMessage`: 状態、影響、次の操作、待機条件
- `StatusBadge`: 短い状態ラベル。説明の代用にはしない
- `EntityCard`: 識別情報、事実、状態、単一の次操作
- `ConfirmationPanel`: 対象、金額、期限、取消条件、確定操作
- `FieldError` / `ErrorSummary`: 入力欄エラーとページ要約

## 8. ページ横断の操作骨格

Public、Home、Studio、Opsは色や情報密度を同じにする必要はないが、利用者が読む順序は統一する。
各ページは原則として次の順で構成する。

1. 現在位置と対象
2. この画面で分かること
3. 現在状態または主要指標
4. 一つの主要操作
5. 記録、履歴、補足

- Studioの下層画面は、Creator概要、ファン全体の輪郭、提供物、収益の現在位置と相互導線を持つ。
- Fanプロフィールは、`プロフィールを保存 → 共有先と項目を選択 → 共有履歴を確認`の順に分ける。入力しただけでは共有されないことと、共有されない情報を最上部で示す。
- Opsの一覧は、単なる箇条書きではなく、対象、理由、状態、期限、識別子を一件のケースとして整列する。入口では審査、決済確認、精算処理の件数と優先対象を分ける。
- PublicのFan・Creator説明画面は、利益、現在利用できる機能、開始手順、役務・公開範囲の境界、開始操作の順で構成する。
- 空状態は通常のデータ領域と同じ位置に置き、空である理由と次の一手を一つだけ示す。
- 320px幅では主要指標、フォーム、カード、操作を一列にし、主要操作を横スクロールの奥へ置かない。

## 9. 状態・エラー・決済のルール

すべての非同期画面は、少なくとも次の状態を設計する。

| 状態 | 必ず示すもの | 禁止 |
| --- | --- | --- |
| loading | 対象と待機中であること | 空データとして表示 |
| empty | なぜ空か、次にできること | 何もない画面だけを表示 |
| processing | 開始した操作、二重操作防止 | 再送ボタンを無条件に表示 |
| pending | 何を待つか、再課金不要、再確認方法 | 完了・発行済みと表示 |
| success | サーバー確定結果、記録、次の導線 | クライアント成功だけで確定扱い |
| attention | 原因、影響、期限、復帰方法 | 赤色だけで警告 |
| unauthorized | 最小限の説明、戻る・ログイン | 対象の存在を推測できる詳細 |

決済・更新・返還・再発行・出金・返金は、確定前に対象、金額、期限、取消条件を表示する。
Webhook反映待ちは完了と表示せず、再課金や二重送信を誘発しない。

## 10. レスポンシブとアクセシビリティ

- 最小幅は320px。主要操作を横スクロールなしで完了できる。
- タップ領域は44px以上とする。
- キーボードで到達・操作でき、フォーカス位置が見える。
- `main`、ページ見出し、ラベル、エラー要約、ライブリージョンを対象状態に応じて持つ。
- 色を無効にしても状態、エラー、必須、選択中、操作可能性を判断できる。
- `prefers-reduced-motion` と forced colors を壊さない。
- 表や台帳は、横スクロールを許す場合でも主要な確定操作を横スクロールの奥へ隠さない。

## 11. 文言ルール

### 使う

- 公式な支援関係の記録
- 証票、現在の保有者、支払済み期限、次回決済日
- 同意した項目だけを対象のクリエイターへ開示する
- 反映を確認中。再度支払わず、履歴を確認する

### 使わない

- 会える、必ず返信がある、特別扱いされる、あなた専用
- 投資、配当、元本保証、値上がり、確実に価値が上がる
- 選ばれし者、ファン順位、上位者だけ
- 証票と別契約の役務を、同じ特典一覧へ混ぜる表現
- 原因、影響、復帰方法のない「エラーが発生しました」

## 12. 合格条件の分類

デザインレビューの判定は、次の3種類を混ぜない。

| 分類 | 検証者 | 合格根拠 |
| --- | --- | --- |
| 機械検証 | LLM・CI | コマンド出力、静的解析、テスト、ビルド |
| 実画面検証 | LLM・レビュアー | 指定幅・指定状態の実画面、スクリーンショット、操作結果 |
| 審美・理解検証 | 独立レビュアー | ルールID付き所見と改善理由 |

機械検証だけで「洗練された」「5秒で理解できる」と判定しない。
実画面を見ていない状態で、視覚検証を完了扱いにしない。
スクリーンショットを取得できない場合は`NOT VERIFIED`であり、`PASS`ではない。

### ルールIDと証拠の対応

| ルール | 最低限必要な証拠 |
| --- | --- |
| D-01〜D-06 | 正本仕様の参照、対象ロール・境界のコード確認、該当状態の実画面 |
| D-10〜D-13 | 画面契約、DOM・状態分岐のコード確認、1440/390/320pxの実画面 |
| D-20〜D-23 | CSS・コンポーネントの静的検索、アクセシビリティ検査、実画面 |
| シェル別ルール | ルート・認可・APIのコード確認、許可/拒否ロールの実画面 |
| 状態・エラー・決済 | 状態遷移・API・テスト、成功/失敗/反映待ちの実画面 |
| レスポンシブ | 320/390/1440pxの実画面と操作結果 |

コード確認だけで、折返し、視認性、誤認、印象の合格を証明しない。実画面確認だけで、認可、
状態確定、個人情報保護、二重操作防止の合格を証明しない。

## 13. 既知の移行対象

2026-08-13時点で、構造再構築により解消した差分と、なお残る差分を分けて記録する。解消済みでも、実画面証拠がない状態を適合済みとは扱わない。

- Public一覧、無料証票入口、旧Creator/Supporter/Admin UIは停止・統合し、個別リンク、`/entry/[publicLinkId]`、四つのシェル、Homeのread model、`/ops`へ移行した。個別リンクの実データ表示と有料checkoutはB-01の手数料仕様確定まで公開しない。
- Publicトップはキャッチコピーだけを主役にせず、証票の対象・状態・期限・来歴というプロダクトモデルの表示例を置く。実在の公開一覧と誤認させない。
- `app/globals.css`の共通sectionカードを廃止し、対象別の事実ブロック・行・確認領域へ移行した。共有部品の契約と全画面の状態表現は継続確認が必要である。
- CIにはアクセシビリティ静的検査があるが、視覚回帰検査とfixture付きの認証済み実画面検査はない。
- `npm run test:integration`は隔離作業コピーにテストDB接続情報がないため、未実行である。

したがって、既存画面の修正では「既存だから正しい」とせず、変更範囲に関係するルールIDを再評価する。
