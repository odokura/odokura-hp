# XXGGLL セキュリティ

## 依存関係・秘密値検査

- 実装リポジトリの依存関係は、コミット済みのlockfileを正本として再現可能なインストールを行う。
- push、Pull Requestおよび定期実行で、high以上の依存関係脆弱性監査と追跡済みテキストの秘密値検査を実行する。検査結果に秘密値、個人情報、決済詳細を出力しない。
- high/criticalの脆弱性を例外扱いする場合は、対象パッケージ、影響範囲、理由、担当者、登録日、期限、次回確認日、対応方針をIssueまたは変更レビューに記録する。期限切れの例外は更新、代替または影響機能の停止を行う。
- GitHub Actionsの既定権限は`contents: read`に限定する。GitHubのSecret Scanning・Push Protectionなど外部リポジトリ機能を利用できない場合も、CIの秘密値検査を継続し、未達の外部条件を完了扱いにしない。
- 実装リポジトリにこの仕様の複製となるセキュリティ方針・保持方針・コンテンツ安全方針を作らず、必要な手順や検証結果からこの正本へリンクする。

## 認証・認可

- 利用者（user）はメール等の最小限の情報でアカウントを作成する。パスワードはハッシュ化して保存し、平文・
  復元可能な形では保持しない。決済手段はトークン化して決済代行に委ね、自社では保持しない。
- アカウント作成・証票の購入・保有・譲渡に年齢制限は設けない。全年齢が利用できるサービスとして設計する
  （下記「年齢確認について」）。
- 運営担当者（`account.ops_role = 'admin'`）がOpsへ入るには、スマートフォンを含む利用者所有のパスキー（WebAuthn/FIDO2）を必須にする。認証器は利用者検証（生体認証または端末PIN）を必須とし、期待するchallenge、RP ID、Origin、credential public key、署名をサーバー側で照合する。メール、パスワード、X OAuth、メール再設定、SMS、通常アカウントのログイン済みCookieをOpsログインの代替・復旧手段にしてはならない。
- パスキーは`admin_passkey_credential`に公開鍵、credential ID、利用状態だけを記録し、秘密鍵、生体情報、端末のロック解除情報を受け取らない。スマートフォン同期型パスキーを許可するが、利用者検証なしの認証器、未登録credential、失効済みcredentialを拒否する。署名カウンタを提供するcredentialでは減少・再利用を異常として記録し、当該セッションを確定しない。カウンタを提供しない同期型credentialは値だけで拒否せず、backup状態を記録して別の認証要件を弱めない。
- Opsの認証開始challengeは推測困難な一回限りの値とし、サーバー側でハッシュだけを保存し、開始したブラウザに結び付けて5分で失効させる。成功・失敗・期限切れを含め、challengeを再利用してOpsセッションを作成してはならない。認証開始と失敗の応答は、adminアカウント・credential・失効理由の存在を示さない。
- Opsの認証開始challengeと登録用の事前認可は、IPを認証要素に使わず、IP単位と全体のレート制限・同時発行上限を設ける。challengeは比較と一回消費を単一の更新で行い、`consumed_at IS NULL`かつ有効期限内の場合だけ消費する。期限切れ・消費済みのchallengeと事前認可は定期削除し、削除処理・拒否件数を監査する。
- Opsは公開利用者向けのログインとは別のHTTPS Originとする。環境ごとに`OPS_ORIGIN`を完全一致のHTTPS URL、`OPS_RP_ID`をそのURLのホスト名として設定する。本番起動時にHTTPS、パス・クエリ・フラグメントを含まないこと、両設定のホスト名一致を検証し、不一致なら起動しない。親ドメイン・ワイルドカードのRP IDを使わず、リバースプロキシはこのHostだけをOpsへルーティングし、他のHost headerをアプリケーション到達前に拒否する。`/ops/sign-in`だけはパスキー認証開始のために到達可能とするが、Public、Home、Studioのナビゲーション・セッション応答・通常の認証画面からOpsの存在、adminロール、credentialの有無を示さない。認証済みOpsページ、旧`/admin`配下、`/api/admin`配下は、有効なOpsセッションがない要求へ理由を区別しない`404`を返す。管理APIは入力解析、DB・外部決済の構成確認、業務処理より先にこの確認を完了する。
- Opsセッションは通常の`auth_session`と別の`admin_session`に保存し、Cookieも`Secure`、`HttpOnly`、`SameSite=Strict`、`__Host-` prefixを満たす専用名にする。通常セッション、Cookie差し替え、利用者・Creatorのセッション発行ではOpsの認可を満たさない。通常セッションの全失効（ログアウト全端末・パスワード変更を含む）は、同じaccountのOps sessionも失効する。全Opsのread/write要求は、共通のOpsセッション検証で現在の`admin_session`、紐づくcredentialの失効状態、`account.ops_role='admin'`、accountがactiveであること、アイドル15分、発行から8時間を同一要求内で再照合する。credential失効・adminロール解除と該当`admin_session`全件の失効は同一DBトランザクションで行い、ロール解除はDBトリガーでも強制する。ロールを再付与しても過去のcredential、Ops session、未完了登録、challengeは再利用できない。更新操作は認可確認から確定まで同じトランザクションで対象セッションとaccountをロックする。
- 返金、送金、強制失効、プログラム終了などの高リスクOps操作は、5分以内に完了したパスキーの再認証をサーバー側で確認する。通常利用者の高リスク操作に必要なパスワード再認証とはセッション、証跡、失敗応答を共有しない。
- `ops_role='admin'`の付与、最初のパスキー登録、全credential喪失後の復旧、ロール解除は、通常の公開Web APIでは扱わない。Railwayの多要素認証済み個人アカウントが、稼働中の対象サービスへ対話的SSH接続して実行する運用手順だけが、対象account、確認済みのRailway個人アカウント、理由、有効期限を記録した一回限りの`admin_passkey_enrollment`を作成できる。実行前に`railway whoami`とRailwayの操作監査で個人アカウントを照合し、入力する実行者名はこの照合結果と一致させる。登録リンクの秘密値は対話端末だけに表示し、URLフラグメントで受け渡す。`Referrer-Policy: no-referrer`の専用画面がTLSで一度だけ送信し、サーバーは有効な登録記録を原子的に消費して、開始ブラウザに結び付く5分以内の`__Host-`事前認可Cookieを発行する。そのCookieを持つ`/ops/enroll`だけでWebAuthn登録challengeを発行する。リンク、Cookie、challengeのいずれかがない要求と失敗理由は同じ`404`とする。
- 既存adminのcredential追加・削除は、有効なOpsセッションだけでは行えない。対象accountの現在有効なcredentialによる5分以内の新しいパスキー再認証を完了し、再認証、adminロール、credentialとセッションの失効状態を同じDBトランザクションで再確認した場合だけ確定する。追加・削除の成功は監査する。紛失・侵害または全credential喪失後の復旧では、旧credential、全Opsセッション、未完了登録、未消費challengeを先に同一トランザクションで失効し、新しい一回限りの登録だけを発行する。メール等による自動復旧を行わない。
- 運営担当者がユーザー画面を確認する場合は、admin専用の読み取り専用ビューで一人の対象を明示して開く。ユーザー本人のセッション発行、Cookie差し替え、なりすまし、ユーザー向け更新APIの管理者バイパスを実装しない。詳細閲覧は`audit_log_entry`へ記録し、認証秘密、OAuthトークン、セッション秘密、パスワードハッシュ、決済手段を返さない。
- 運営担当者がCreator画面を確認する場合は、admin専用の読み取り専用ビューで一人の対象を明示して開く。Creator本人のセッション発行、管理権限の差し替え、Creator向け更新APIの管理者バイパスを実装しない。詳細閲覧は`audit_log_entry`へ記録し、個人ファン一覧、未同意属性、Stripe Connected Account ID、銀行口座、本人確認書類、秘密値を返さない。
- OpsはRailway上の本番アプリケーションがサーバー側でDBへ接続して処理する。ブラウザ、ローカルPC、パスキー認証器へ`DATABASE_URL`、DB接続資格情報、Railwayの管理資格情報を配布せず、PostgreSQLの公開接続を有効にしない。Ops APIはブラウザからのDB直接接続を受け付けず、Opsセッションを検証したサーバー処理だけがプライベートネットワーク経由でDBを利用する。
- Railwayのプロジェクト管理権限はOpsより上位の信頼境界として扱う。共有アカウントを使わず、個人を識別できる最小権限のアカウントだけを許可し、利用可能な最もフィッシング耐性の高い多要素認証を必須にする。環境変数、デプロイ、ドメイン、メンバー権限、DB公開設定の変更は監査・通知し、担当終了時は即時に権限を外す。ソースコードだけの漏えいではパスキー秘密鍵、Railwayの管理資格情報、DB接続資格情報、登録用の一回限りの秘密値を得られない設計にする。
- 端末名、IPアドレス、Host header、User-Agent、ブラウザ指紋をadmin本人の認証要素として扱わない。端末の利用制限を導入する場合は、別途、コピー不能な端末鍵とその失効・復旧手順を正本へ追加するまで有効化しない。
- 役割ベースアクセス制御（RBAC）を用い、[要件](./requirements.md)の権限マトリクスをサーバー側の認可判定に
  そのまま対応させる。フロントエンドでの表示制御だけに頼らない。
- 運用機能はadminロールに集約する。`ops_role` の追加による役割分割は行わない。
- 管理画面は一般利用者向けAPIとログインセッションを分け、運営アカウントの侵害が利用者アカウントへ直接
  波及しないようにする。専用HTTPS Originは必須とするが、バックエンドを別インフラへ分離することは必須にしない。
- クリエイターの精算先変更など、金銭の受取先に関わる操作には追加の確認ステップを挟む。
- セッションには発行から30日の絶対期限と最終利用から7日のアイドル期限を設ける。ログイン・登録・OAuth完了・
  資格情報変更後は新しいセッションを発行し、旧セッションを使い回さない。
- 通常利用者の高リスク操作は、サーバー側で現在の通常セッションの再認証時刻を確認する。対象はOAuth連携解除と精算申請とし、パスワード再認証から15分を超えている場合は`reauthentication_required`で確定を止める。パスワード値や再認証秘密値は保存・返却しない。adminによる返金・送金などのOps操作は、この通常再認証を使わず、上記の5分以内のパスキー再認証を必須にする。
- パスワード変更自体は現在のパスワード（初回設定を除く）を必須とし、成功後に全セッションを失効して新しい
  現在セッションだけを発行する。OAuth専用アカウントはパスワード設定後に再認証可能とする。
- 通常利用者の設定トップは、現在のaccountに結び付いた最小限のread modelだけを返す。メール、認証方法、セッション、プロフィール共有状態の更新は、現在の通常セッション、CSRF対策、対象所有権、必要な再認証を同一のサーバー側処理で確認し、クライアントのaccount ID、session ID、再認証済みフラグを認可根拠にしない。
- メール変更は新しい連絡先の確認完了まで旧連絡先を有効に保ち、確認成功後に通常セッションを全失効して現在ブラウザだけへ新しいセッションを発行する。X連携解除は直近の再認証と別のログイン方法の残存を確認し、最後の認証方法を消す操作を拒否する。パスワード変更、メール変更、連携解除、全端末ログアウト、アカウント閉鎖の結果を監査するが、パスワード、トークン、Cookie、メールアドレス本文、決済手段を監査ログへ記録しない。
- 通常利用者の設定画面でOpsのパスキー、`admin_session`、Railway資格情報、DB接続資格情報を表示・操作できない。Ops認証は専用Origin・専用セッション・登録済みパスキーの境界を維持し、通常のアカウント設定から到達可能にしない。
- アカウント閉鎖は、保有中XXGGLL、処理中決済、未解決ケースを確認してから、直近の再認証と明示的確認を要求する。台帳・証票来歴・必要な監査記録を削除・改変せず、個人プロフィールの開示と通常・Opsセッションを確定後に失効する。保持・匿名化・再開可否がデータモデルへ定義されるまで、完了したように見える退会操作を提供しない。

## 年齢確認について

- アカウント作成、証票の購入・保有・譲渡には、年齢確認・年齢制限を一切設けない。全年齢向けサービスとして
  設計する。
- 生年月日・年齢を通常の登録項目として収集・保存しない。
- 法令上の年齢確認が必要な対象コンテンツ・役務は、本サービスで提供しない。

## 個人情報・属性データの保護

- プロフィールは自己申告として扱い、収集項目を構想の許可リスト（アカウント名、出身国・地域、年代、職業/業界、興味、応援理由、
  活動歴、希望する呼称等）に限定する。人種・民族、宗教、政治的信条、病歴、障害、性的指向、金融口座、
  正確な住所、電話番号、個人メールアドレス、決済カード情報は、通常のプロフィール項目として収集・保存しない。
- 発行者への個人開示は、`certificate.current_holder_account_id`、当該`issuance_program`の発行者、Creator owner権限を同じサーバー側クエリで結合して確認したときだけ返す。Creator staff、他Creator、前保有者、Creator横断画面・API、キャッシュだけでの再表示には返さない。譲渡、返還、運営回収で現在保有者が変わった要求は、旧保有者の値を直ちに返さない。
- 現在保有者について、アカウント名と出身国・地域は発行者へ自動開示する。その他のプロフィールは`account_profile.creator_disclosure_enabled`が有効な場合だけ返し、無効化後の要求では即時に除外する。プロフィールの編集は、共通公開フラグを有効にしない限り任意プロフィールを開示しない。
- 発行者へ表示する取得時購入額は、当該現在保有者・当該XXGGLLの取得確定時に`relationship_acquisition`へ記録した価格から返す。税、決済・プラットフォーム手数料、継続支援、証票支援、グッズ購入、別のXXGGLL、前保有者、Creator報酬の金額を混在・推定・集計して返さない。
- 発行者向けのCSV等の一括エクスポート、横断検索、外部連絡先への変換・同期は許可しない。個人を特定する開示は発行プログラム詳細のread-only区画に限る。
- 自由記述（応援表現、希望共有）は、URL・電話番号・メールアドレス・SNS IDなど私的連絡先のパターンを
  自動検出し、投稿前に警告または保存を拒否する。検出をすり抜けた場合に備え、通報・非表示の経路を用意する。
- 証票支援の個々の支払い記録（`ledger_entry`のcertificate_boost行。誰が・いつ・いくら払ったか）は、
  支払った本人とadminだけが参照できる。買い手・将来の保有者を含む他の利用者に公開してよいのは、証票に
  記録された匿名化累計額（`certificate.boost_total_amount`）だけとする
  （[構想](../concept/benefits/content.md)の「証票支援」、[データモデル](./data-model.md)）。
- 取得時のXフォロワー数はDBトランザクションを開く前に正規連携元から取得した、取得直前5分以内の公開集計値と
  観測時刻だけを保存する。連携の遅延・失敗でXXGGLL取得を止めず、`unavailable`とし、推定値、手入力値、古い値で補完しない。
- グッズコードは正規販売元から購入確定と注文参照を受領した場合だけ発行する。注文参照はハッシュ化して
  二重発行を防ぐ。コードは推測困難な一回限りの値とし、DBには照合用ハッシュだけを保存する。登録時は現在保有者と
  対象プログラムをサーバーで照合し、生コードをアクセスログ、監査ログ、分析イベント、エラーへ出さない。
- グッズ購入履歴は登録した本人の関係記録であり、XXGGLLの譲渡先へ引き継がない。Creatorには、個別表示に
  必要な同意と権限がない限り、商品傾向の集計だけを返す。

## 決済・台帳のセキュリティ

- カード情報・銀行口座情報は自社インフラを通過させない。決済代行のトークン化されたAPIを通じて行う。
- すべての決済操作は冪等キーを必須とし、二重送信・再試行による二重課金を防ぐ。
- 買い手の支払いは、決済成立時点でクリエイター・前保有者へ即時分配しない。いったん運営のプラットフォーム
  残高へ集約し、`ledger_entry` で決済とクリエイター報酬を記帳する
  （[データモデル](./data-model.md)、[アーキテクチャ](./architecture.md)）。クリエイター報酬は、購入価格・運営売上との
  配分率を約定せず、決済手数料、返金・異議申立ての見込みおよび運営上のリスク留保を織り込んで取引ごとに算定する。
- クリエイターへの実際の送金は、`payout_request` による出金申請があったときだけ実行する。二次流通の前保有者には
  `reissue_credit_entry`へ再発行クレジットを付与し、送金しない。決済の
  都度クリエイター側の確認を求めず、初回の出金申請の中でだけStripeのホスト型オンボーディングへ
  進む。これにより、購入が積み重なるだけでは運営側にもクリエイター側にも作業・費用が発生しない。
- 送金前に、`creator_profile.stripe_connected_account_id`、`stripe_payouts_enabled_at`、`payout_country`およびAccounts v2のrecipient transfer capabilityをサーバー側で確認する。銀行口座情報・本人確認書類をアプリケーションDBへ保存しない。
- 出金申請額は、決済確定日から90日を経過し、確認中の`payment_review`がない対応する `ledger_entry` の未精算合計を
  超えてはならない。申請済み・オンボーディング中・
  処理中の申請も残高から予約控除し、同じ分配金への重複申請を防ぐ（[データモデル](./data-model.md)の整合性ルール）。
- 再発行クレジットは、運営が契約相手となる一次発行・再発行・継続支援にだけ利用できる。現金化、払戻し、
  チャージバック、他者移転、追加商品・VIP・物販その他クリエイター個別のサービスへの利用をサーバー側で拒否し、
  付与日から6か月後に未使用残額を失効記帳する。再発行の購入決済自体が取消・返金・チャージバックにより
  成立しなくなった場合だけ、対応するクレジット付与を取消記帳する。クレジットを現金または送金可能残高へ
  変える処理は持たない。
- 返金は元取引を参照する取消行として記録し、既存の台帳行を書き換えない。台帳の直接編集は行わない。購入者の
  申告だけでは返金・取消しを確定せず、決済事業者・カード会社からの異議申立て、不正利用を示す合理的な資料又は
  公的機関からの要請を`payment_review`に記録して確認する。確認は通常90日、対象取引は最長180日までとする。
  確認中に返金が確定した場合は未精算額だけを取り消す。精算可能額として確定・支払済みの報酬については、通常の
  購入者返金・チャージバックを理由にクリエイターから相殺・回収せず、運営残高・運営のリスク留保で負担する。
- 決済代行からのWebhookは署名検証を行い、検証に失敗したイベントは処理しない。
- Stripe Webhookは、署名検証後のイベントIDだけを`stripe_webhook_event`へ記録し、本文は保存しない。
  同じイベントIDは再処理しない。Accounts v2のrecipient capabilityイベントだけを用いて
  `creator_profile.stripe_payouts_enabled_at`へ反映し、対象外・未対応のイベントは送金や台帳を変更せずに処理済みとする。
- 在庫仮押さえ（15分）は排他制御のもとで行い、同一証票・同一枠に対する同時購入が1件だけ成立するようにする。
- 返金・出金申請の承認はadminロールが行い、操作は監査ログに記録する。複数人承認の仕組みは設けない。

## 不正対策

- 待機リストの通知先はハッシュ化して保存し、同一連絡先の重複登録程度の簡易チェックに使う。個人を長期
  追跡する仕組みは持たない。
- 購入・出品・ログインには基本的なレート制限を課し、単純な連続試行を抑止する。
- チャージバック・返金が特定のアカウント・クリエイターへ集中した場合に、adminが手動で確認できるよう
  台帳画面から検索できるようにする。自動スコアリング・自動凍結は行わない。
- `payment_review`は、決済事業者・カード会社からの通知、不正利用を示す合理的な資料又は公的機関からの要請が
  ある場合だけ作成する。購入者からの申告だけでは作成せず、返金の判断・根拠・保留期限・操作担当を監査ログへ残す。
- 違反調査中のアカウントは、譲渡・継続決済・属性共有・公開表示・固定コンテンツ閲覧を停止できる状態
  （`account.status = investigation_hold`）を持つ（[取引ルール](../concept/general/transaction-general.md)
  の「調査・違反」）。
- 二次流通の不正監視を目的とした専用の検知基盤・スコアリングは作らない。ただし、
  [価格・発行数の算出](../concept/general/pricing.md)の二次流通基準価格の計算は「関連当事者間取引・自己売買を
  除く」ことを前提にしているため、同一決済手段・同一名義など安価に判定できる範囲の自己売買は、価格算出の
  入力データを作る段階で除外する。それ以外の不正調査は、
  台帳の記録（誰が誰から買ったか）をもとに事後対応する。

## コンテンツ・メッセージの安全性

- 応援表現・自由記述・VIP希望共有は、投稿前の自動検査（禁止表現、脅迫、性的要求、面会要求、個人情報、
  なりすまし）と、投稿後の通報による人手調査を併用する（[関係記録・コンテンツ](../concept/benefits/content.md)
  の「安全・権利」）。
- 自動検査は再現可能なルールベースとし、私的連絡先、場外決済、性的要求、面会要求、脅迫・恐喝、差別・ヘイト、
  詐欺・勧誘を検出対象とする。検出カテゴリは調査に必要な最小限のメタデータだけを記録し、本文を監査ログへ
  複製しない。
- 固定コンテンツは公開前の権利確認・審査対象とし、権利侵害や安全上の問題が判明した場合は
  証票自体を維持したままコンテンツだけを停止できるようにする。
- 通報・ブロック・非表示は1操作で完結させ、以後の調査はadminが行う。クリエイターに本人調査や外部連絡を
  求めない。
- ルールを変更するときは、対象カテゴリ、変更理由、誤検出の想定、許可・拒否・権限なし・非表示・重複通報の
  テスト結果を記録する。テストに実在する連絡先・個人情報・秘密値を使わない。

## VIPコンシェルジュ・匿名性の保護

- VIP・ExtraVIPユーザーの希望・属性は、まず運営が受け取り、クリエイターへ渡す前に、氏名・連絡先等の本人
  特定情報を除いて整理する（[VIPコンシェルジュ運用](../concept/vip/vip-concierge.md)の「共有しない情報」）。
- ExtraVIPの匿名打診では、最初の打診にユーザーを特定できる情報を一切含めない。特定可能な情報を含む
  メッセージがクリエイター側へ渡る前に、自動チェックの段階を設ける。
- コンシェルジュのケース閲覧・共有操作はすべて監査ログへ記録する。
- クリエイター・提供者側の閲覧者にも最小権限を適用し、事務所単位の一括閲覧権限を既定で与えない
  （[VIPクリエイター](../concept/vip/creator-vip.md)の「属性情報の取扱い」）。
- 運営担当者・クリエイターの私的SNS、私用連絡先、外部DMは連絡経路として使わない。すべての連絡はアプリ内
  スレッドを経由させ、記録に残す。

## 運営権限の統制と監査ログ

- 証票の強制失効、プログラム終了の確定、返金は、いずれもadminロールに限定し、
  操作の全体を監査ログへ記録する。提案者と承認者を分ける複数人承認は行わない。
- 次を監査ログの必須記録対象とする。
- 発行者向けプロフィール公開フラグの有効化・無効化
- Creator ownerによる現在保有者の個人開示閲覧
  - 台帳への記帳・返金
  - 証票の状態遷移（発行・譲渡・継続・回収・終了・アーカイブ）
  - 管理画面での閲覧・操作（個別プロフィール閲覧を含む）
  - 認証の失敗、重大操作の実行
- 監査ログ（`audit_log_entry`）は追記専用とし、アプリケーションのDB接続ロールにUPDATE/DELETE権限を
  与えない。ハッシュチェーン等の改ざん検知基盤は作らない。

### 取引監視

- 台帳（`ledger_entry`）、証票の状態遷移、運営操作を漏れなく監査ログへ記録し、後から誰が・
  いつ・何を行ったかを追跡できる状態を常に保つ。
- 異常な取引パターン（同一アカウントへの返金集中等）は、自動遮断ではなくadminが台帳を検索して確認する
  運用とする。

## データ保持・削除

| データ区分 | 保持方針 |
| --- | --- |
| 証票・来歴（certificate / certificate_event） | プログラム終了後も期限なく保持する（[取引ルール](../concept/general/transaction-general.md)） |
| 台帳（ledger_entry） | 会計・監査目的で法定期間保持する。削除は行わない |
| プロフィール・発行者向け公開設定（account_profile / profile_creator_disclosure_event） | 共通公開フラグの無効化後は任意プロフィールを直ちに発行者向け応答から除外する。アカウント名・出身国地域・当該取得時購入額は現在保有者である間だけ返す。公開設定の変更履歴と閲覧監査は残す |
| メッセージ・応援表現 | ユーザーの削除操作に応じて非表示化する。安全対策・紛争対応に必要な期間は調査記録として保持し得る |
| 監査ログ | 長期保持する。削除は行わない |
| セッション | アイドル7日または発行から30日で失効する。資格情報変更または全端末ログアウト時は失効させる |
| メール確認・パスワード再設定・OAuth state | ハッシュ化した短期トークンだけを保持し、使用・期限切れ後は失効させる |

削除依頼は、対象アカウント、法的保留、未解決の決済・通報を確認してから処理する。削除できない台帳・監査行は、
本文や連絡先を追加せず、関連アカウントを匿名参照へ置き換える方法を個別に記録する。OAuth access token、
カード番号、Stripeの秘密値、本人確認書類は保存しない。利用者向けエラーや監査ログにはメールアドレス、
メッセージ本文、秘密値を出さず、追跡が必要な場合はサーバー生成の要求識別子だけを使う。

## インフラ・シークレット管理

- 通信は全経路でTLSを必須にする。
- 決済代行への認証情報はシークレット管理サービスで管理し、アプリケーションコードや設定ファイルに
  平文で置かない。
- 本番・ステージング環境を分離し、本番データをステージングへ複製する場合は台帳・PII相当項目を
  マスキングまたは除外する。

## インシデント対応

- 調査中のアカウントは `investigation_hold` として、譲渡・継続決済・属性共有・公開表示・固定コンテンツ
  閲覧を停止する。違反が確認されなければ直ちに復帰し、支払済み期間を停止日数分延長する
  （[取引ルール](../concept/general/transaction-general.md)の「調査・違反」）。
- 個人情報漏えい、脅迫、つきまとい等の緊急申告は24時間受付とし、即時アクセス停止を可能にする
  （[VIPコンシェルジュ運用](../concept/vip/vip-concierge.md)の「応答基準」）。
- 情報漏えいが疑われる場合は、内部エスカレーション、影響範囲の特定、必要な利用者・監督官庁への通知を行う。
