# XXGGLL アプリ仕様

本カテゴリは、[構想](../concept/overview.md)で確定した業務ルールを安全に実装するためのシステム仕様である。
証票のランク・発行上限・価格算出・KYC発動条件・役務境界などの**業務ルールは構想が正本**であり、本カテゴリでは
再掲しない。本カテゴリが正本とするのは、その業務ルールを満たすシステム構成、データモデル、セキュリティ管理策、
実装前に確認すべき技術検証である。

## 設計の芯: 小規模運用を前提にする

XXGGLLは、大規模なフィンテック基盤ではなく、小さな運営体制で回せる規模のサービスとして設計する。実際の
運用は少人数（場合によっては1人）の運営が担うことを前提とし、多数の専任ロール、承認ワークフロー、
マイクロサービス分割、改ざん検知基盤のような、規模に見合わない運用体制・分散構成は最初から作らない。
決済・KYC・監査ログなど法令や利用者保護に関わる最低限の管理策は維持しつつ、実装は単一の小さな
アプリケーションとしてまとめる。詳細は[アーキテクチャ](./architecture.md)、[セキュリティ](./security.md)を
正本とする。

## 前提と適用範囲

- 対象は一般ルート（無料・一般・上級・最上級）とVIP・ExtraVIPルートの両方。証票・台帳・同意・KYC・
  監査ログは共通のデータモデルを使う。
- S1別商品・S2 VIP・ExtraVIP役務は証票本体から分離するという構想の原則を、データモデル・台帳・決済フロー
  でも分離した形で実装する。
- 対応言語は日本語のみとする。
- アカウント作成・証票の購入・保有に年齢制限は設けない。全年齢が利用できるサービスとして設計し、
  個別の対象コンテンツ・役務に法的な年齢確認が必要な場合だけ、その対象範囲でKYCを行う
  （[セキュリティ](./security.md)）。
- 本カテゴリはセキュリティを主眼に置くが、小規模運用の前提を踏まえ、規模に見合わない管理策は追加しない
  （[決定ログ](./decisions.md)）。ビジュアルデザイン・詳細なUIワイヤーフレームはスコープ外とする。

## 次工程

構想・アプリ仕様・[利用規約](../terms-of-service.md)/[プライバシーポリシー](../privacy-policy.md)のドラフトは
一通り書き終えている。残る作業は性質の異なる4種類に分かれ、(1)〜(3)は文書作成だけでは完結できない。

### 1. 法務レビュー（外部の専門家が必要）

現時点の確認対象は、次の2点である。決済・クリエイター精算の方針は
[クリエイター報酬・精算](./legal-review-payment-secondary-termination.md)を正本とし、一覧の正本は[決定ログ](./decisions.md)とする。

1. **条件付きKYCと個人情報**: KYCが必要な対象コンテンツ・役務を実際に公開する時だけ、法的根拠、保存期間、
   削除・第三者提供、Didit等への越境移転を確認する。KYC不要のMVPでは実施しない。
2. **S1/S2の個別契約**: 別商品またはVIP・ExtraVIP役務を公開する時だけ、提供条件、取消・返金、事故・
   知的財産権、コンシェルジュ記録の取扱いを、その商品・役務の内容に応じて確認する。

以下は、現行仕様では独立した法務確認項目から外した。一次購入は運営が売主・代金受領者であり、クリエイターへの
分配は別契約に基づく支払債務とした。二次流通も運営の再発行方式で、前保有者への現金送金・利用者間残高移転は
行わない。再発行クレジットは、運営提供サービスだけに使える6か月失効・現金化不可の仕様とし、返金・
チャージバックを行わない。金融商品としての元本・利回り・利用者への収益分配・買戻しも設けない。

### 2. ベンダー確認（実際に問い合わせが必要）

[ベンダー選定](./vendor-selection.md)の「未確定事項・次アクション」に集約済み。特に優先度が高いのは、
Stripeの事業審査と、USD建て決済から日本・海外クリエイターのConnected Accountへ送金する際の対象国、
サービス契約、通貨、為替・手数料、送金経路の確認である。これは法的分類の確認ではなく、実際に送金可能な
国・通貨の対応表を確定するためのベンダー確認とする。

### 3. 技術検証（実装に着手して確認）

[技術検証計画](./tech-verification.md)のV-1〜V-5。特にV-1（決済の受領と出金の分離）とV-4（在庫仮押さえの
アトミック性）がMVP着手のブロッカーになり得る。

### 4. 運用を始めてから判断すればよい事項

- クライアントのプラットフォーム（Web単独かネイティブアプリを含むか）
- 運営体制が拡大した場合の役割分割・承認ワークフローの要否

1〜3が一通り片づいた段階で、実装リポジトリの作成・issue分割へ進む。
