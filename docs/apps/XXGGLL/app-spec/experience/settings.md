# XXGGLL 設定画面仕様

設定は、利用者が自分のアカウントを安全に理解し、必要な変更・失効だけを実行するためのアカウントコントロールセンターである。ダッシュボード、活動記録、保有XXGGLL、プロフィール編集、Creator管理を一画面へ集めない。

本仕様の結論は明確である。

- `/fan/settings`は読み取り中心の設定概要とし、最初からフォームを表示しない。
- 設定トップは、アカウント情報、安全性、サービスとデータ、アカウント操作の順に固定する。
- 行を選ぶと対象の詳細画面へ進み、編集・再認証・確定は対象画面で一つずつ行う。
- ログイン後の全画面と同じ`SettingsPageFrame`、`PageHeader`、行形式、状態表示を使う。設定だけのカード、背景、ボタン体系を作らない。
- 未実装・未定義の機能を「設定できる」ように見せない。特にメール変更、通知設定、決済カード管理、アカウント閉鎖の完了操作は、サーバー契約と保持方針が確定するまで提供しない。

## 1. 利用者が設定で知りたいこと

設定を開いた利用者は、次の四つを迷わず確認できなければならない。

1. いまの連絡先とアカウント状態は何か。
2. どの方法でログインでき、どの端末がログイン中か。
3. プロフィールが誰へ開示される状態か。
4. 変更・失効・ログアウトを安全に行うにはどこへ進めばよいか。

設定画面に入った直後に、パスワード、再認証、複数の確認ダイアログを同時に表示してはならない。変更対象を選んだ時点で、理由、影響、復帰方法を説明する。

## 2. 画面と責務

| 画面 | テンプレート | 責務 | ここに置かないもの |
| --- | --- | --- | --- |
| `/fan/settings` | `T-SettingsOverview` | 現在値・状態・詳細画面への導線、ログアウト、未提供操作の境界 | 長いフォーム、活動グラフ、保有カード、Creator操作、Ops操作 |
| `/fan/settings/security` | `T-SettingsDetail` | パスワード、OAuthログイン方法、本人確認、端末の個別終了・全端末ログアウト | Opsパスキー、Railway、DB接続資格情報、決済カード |
| `/fan/profile` | `T-ViewEdit` | アカウント名、出身国・地域、任意プロフィール、発行者への共通公開 | ログイン方法、セッション、支払い履歴 |
| `/fan/activity` | `T-Analytics` | 本人の取得・支払い・返金・保有の振り返り、ユーザーランク | パスワード、メール、公開設定 |
| `/fan/supports/[id]` | `T-Detail` | 一件のXXGGLLの状態、来歴、自動継続・返還 | アカウント全体の設定 |
| `/account` | 互換redirectのみ | 未認証は`/sign-in`、認証済みは`/fan/settings`へ移動し、画面は表示しない | 認証フォーム、認証済み利用者向けの設定フォーム |

`/account`を認証画面または認証済みの設定画面として再利用してはならない。正規の認証画面は`/sign-in`だけとする。旧ルートへ到達した場合は、未認証なら許可済み相対`returnTo`だけを引き継いで`/sign-in`、認証済みなら`/fan/settings`へ移動する。

## 3. 設定トップの完成形

設定トップは[デザイン仕様](./design.md)の認証済みアプリシェル内に表示する。本文の骨格は次のとおりであり、ページごとの独自レイアウトを追加しない。

```text
アカウント / 設定
設定
ログイン、プロフィールの共有、アカウントの安全を管理します。

[成功・エラー・利用制限の状態]

アカウント
  アカウント情報
    連絡先メールアドレス    masked value / 未登録
    プロフィールと共有      現在の発行者数 / 任意プロフィール共有の状態   プロフィールを確認 →
    アカウントの状態        利用中 / 確認中

安全性
  ログインとセキュリティ
    ログイン方法            パスワード / X / Google                    管理 →
    ログイン中の端末        n台                                      端末を確認 →

サービスとデータ
    支払い情報              決済事業者で管理。カード・口座は保存しない
    活動の記録              取得・支払い・返金の記録                     記録を見る →

アカウント操作
    ログアウト              この端末だけを終了                             [ログアウト]
    アカウントを閉じる      保持・匿名化方針が確定するまで完了操作を提供しない
```

各行は「項目名 → 現在値または状態 → 次にできること」の順にする。別画面へ移動する行はリンク、変更・失効・ログアウトはボタンとし、役割を混同しない。

### 3.1 設定トップで表示する状態

- 連絡先メールは、本人向けのマスク値と登録済み・未登録だけを表示する。現行データモデルに確認時刻がない間は「確認済み」と推測表示しない。
- プロフィール共有は、アカウント名・出身国地域が現在保有するXXGGLLの発行者へ自動開示されること、任意プロフィールの共通公開フラグの状態、現在の発行者数を表示する。編集は`/fan/profile`だけで行う。
- ログイン方法は、メールアドレス・パスワード、X、Googleの設定済み状態だけを表示する。OAuth token、provider subject、パスワードは表示しない。
- 端末は有効な通常セッション数だけを表示する。端末の秘密値、Cookie、正確なIPアドレスは表示しない。
- `investigation_hold`はページ上部の状態メッセージとアカウント状態行で説明し、購入・送信・公開が制限されていることを隠さない。
- 支払い情報は「XXGGLLにカード番号・銀行口座を保存しない。決済事業者で管理する」と説明するだけで、空の支払い設定フォームを表示しない。

### 3.2 設定トップに置かないもの

- パスワード変更フォーム、再認証フォーム、OAuth解除確認、端末終了確認。
- 活動グラフ、ユーザーランクの根拠、保有XXGGLLカード、継続支援の操作。
- Creator登録、発行管理、保有者統計、収益、スタッフ権限。
- 通知、言語、タイムゾーンなど、実際の保存・配信・表示切替を実装していない設定。
- 決済カード、銀行口座、Cookie、OAuthトークン、DB接続資格情報、Opsパスキー。

## 4. セキュリティ詳細画面

### 4.1 ログイン方法

`/fan/settings/security`では、現在の方法を一覧で確認し、追加・解除の結果をサーバー確定値で再表示する。

- パスワードは設定済み・未設定だけを表示する。初回設定では現在のパスワードを求めず、変更では現在のパスワードを求める。
- 新しいパスワードは12〜128文字とし、保存後は全通常セッションを失効し、現在のブラウザだけに新しいセッションを発行する。
- X・Googleの追加は既存のOAuth state、PKCE、連携先account束縛を使う。連携解除は直近の本人確認を必須にする。
- 最後のログイン方法を解除させない。解除前にパスワードまたは別の有効なOAuth方法が残ることをサーバーで確認する。
- 通常利用者の画面でOpsパスキー、`admin_session`、`admin_passkey_credential`、Railway資格情報、DB接続資格情報を管理しない。

### 4.2 本人確認

- 高リスク操作の前に、パスワードによるサーバー側の再認証を行う。
- 再認証済みの状態はクライアントのフラグではなく、account sessionの`reauthenticated_at`をサーバーで15分以内に再照合する。
- 再認証成功は「15分間、高リスク操作を実行できる」と表示する。パスワードは保存・再表示しない。
- パスワード未設定のOAuth専用アカウントでは本人確認を実行できないため、先にパスワード設定を案内する。

### 4.3 ログイン中の端末

- 現在の端末、他の有効な通常セッション、最終利用時刻、有効期限、一件ごとの終了操作を表示する。
- URLに含まれるsession IDだけで他人のセッションを終了できない。サーバー側で現在のaccount所有を再照合する。
- 「すべての端末からログアウト」は現在の端末を含む通常セッションを失効し、トップまたはPublicへ安全に戻す。
- 端末終了後に一覧を再取得し、成功表示はDB確定後だけにする。すでに終了済みの対象は、秘密情報を返さず安全な成功・再確認状態として扱う。

## 5. 連絡先・プロフィール・閉鎖の境界

### 5.1 連絡先メール

現行リリースでは、設定トップで登録済み・未登録とマスク値を確認するだけで、メール変更フォームを提供しない。メール変更を追加する場合は、次の契約を先に仕様、DDL、API、テストへ同時反映する。

- 新しいアドレスの確認完了まで現在の連絡先を有効に保つ。
- 変更開始・確認・失敗を監査するが、旧アドレス、新アドレス、確認トークンを監査ログへ保存しない。
- 完了後は通常セッションを失効し、現在のブラウザだけに新セッションを発行する。
- 列挙、CSRF、再送レート制限、確認リンクの期限、未確認値のログイン利用を定義する。

契約がない段階で「変更」「確認メール再送」ボタンだけを表示してはならない。

### 5.2 プロフィールと発行者への共有

- アカウント名と出身国・地域は、現在保有するXXGGLLの発行者全員へ自動開示される。
- 任意プロフィールは、ユーザーが共通公開フラグを有効にした場合だけ、現在保有する全XXGGLLの発行者へ開示される。
- Creatorごと・項目ごとの選択、Publicへのプロフィール公開、発行者からの連絡許可は作らない。
- 現在保有するXXGGLLがなくなった場合、そのXXGGLLに関する開示は直ちに終了する。
- 設定トップには要約だけを表示し、保存は`/fan/profile`の一回の原子的な更新だけにする。

### 5.3 アカウントを閉じる

現行リリースでは完了ボタンを提供しない。保有中XXGGLL、処理中決済、未解決ケース、台帳、証票来歴、監査記録の保持・匿名化・再開可否が未確定のまま、削除に見える操作を実装してはならない。画面下部には、閉鎖が現時点でできない理由だけを説明する。

確定後に実装する場合は、保有・決済・ケースの事前確認、直近の再認証、確認文、冪等性、全セッション失効、プロフィール開示停止、台帳・監査記録の不変性を必須とする。

## 6. APIとデータ境界

設定トップの概要は`GET /api/auth/settings`で取得する。

| 項目 | 応答 | 禁止 |
| --- | --- | --- |
| account status | `active`、`investigation_hold` | admin権限やOps credentialの存在 |
| contact | マスク済みメール、登録済みフラグ | 他accountの連絡先、確認 token |
| authentication | password設定済み、X/Googleのprovider名 | password hash、OAuth token、provider subject |
| sessions | 有効な通常セッション数 | session secret、Cookie、IPアドレス |
| profile disclosure | 任意プロフィール共通公開フラグ、現在の発行者数 | 他人のプロフィール、発行者別の選択権 |

このAPIはCookieの通常セッションから解決した現在のaccountだけを対象とし、クライアントからaccount IDを受け取らない。未認証は401、応答は`cache-control: no-store`とする。DB・Stripe・Railwayの構成確認や検索は、認証確認より前に実行しない。

すべての更新APIは、same-origin/CSRF、入力許可リスト、対象account所有権、再認証要否、成功後のセッション状態をサーバーで確認する。画面の非表示は認可の代替にならない。

## 7. 状態とアクセシビリティ

| 状態 | 表示 | 次の一手 |
| --- | --- | --- |
| 読み込み中 | 対象を含む読み込み中メッセージ | 待つ、再読み込み |
| 未認証 | 設定を確認するにはログインが必要 | 検証済み`returnTo`でログイン |
| 正常 | 現在値、状態、遷移先 | 対象を確認・変更 |
| 利用制限中 | 制限対象、影響、確認先 | 設定または問い合わせ |
| 再認証要求 | 理由、対象、再認証時間 | 本人確認、キャンセル |
| 処理中 | 操作対象、二重操作防止 | 待つ。再送しない |
| 成功 | DB確定後の新しい状態 | 設定トップへ戻る |
| 失敗 | 原因、変更前の状態、復帰方法 | 入力修正、再試行 |

- `h1`は一画面に一つ、`設定`または対象設定名とする。
- 各行は44px以上の操作領域を確保し、モバイルではラベル、現在値、操作名を縦に積む。
- 状態とエラーは色だけで表現せず、`role="status"`または`role="alert"`とテキストを使う。
- フォームのエラーは対象入力の近くへ表示し、再送時に編集前のサーバー状態と入力中の値を混同しない。
- キーボード、320px幅、forced colors、`prefers-reduced-motion`で主要操作を完了できる。

## 8. 受け入れ条件

- `/fan/settings`は`/account`の認証画面を再利用せず、読み取り中心の概要として表示する。
- 設定トップはアカウント情報、安全性、サービスとデータ、アカウント操作の順序と共通行形式を使う。
- `/fan/settings/security`でパスワード設定・変更、OAuth方法の追加・解除、本人確認、個別セッション終了、全端末ログアウトを行える。
- パスワード、OAuth token、Cookie、決済カード、銀行口座、DB接続資格情報、Opsパスキーを画面または設定APIから取得できない。
- プロフィール編集は`/fan/profile`、活動・金額は`/fan/activity`、一件のXXGGLL操作は`/fan/supports/[id]`に分離される。
- 未認証アクセスは設定データを返さず、検証済み継続先を経てログインへ進む。
- メール変更、通知設定、決済手段、アカウント閉鎖は、実装契約がない状態で完了操作を提供しない。
- 他accountのID、session ID、profile IDを指定しても、対象の存在や設定値を返さず、サーバー側で拒否する。
- デスクトップとモバイルで、同じ見出し階層、行順、状態表現、主要操作位置を保つ。
