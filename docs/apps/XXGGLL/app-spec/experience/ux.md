# XXGGLL UX

## シェルと閲覧境界

| シェル | 利用者 | 表示範囲 |
| --- | --- | --- |
| Public | 未認証者 | 製品世界と仕組みの説明、外部案内から開く対象限定の取得ページ、Creator開始、認証 |
| Home | 認証済み利用者 | 本人の保有XXGGLLカード、本人が管理する発行XXGGLLカード、要対応 |
| Studio | クリエイター・スタッフ | 発行XXGGLLの設定、匿名集計、収益、提供物 |
| Ops | 利用者検証必須の登録済みパスキーで発行された専用Opsセッションを持つadmin | 審査、通報、返金、精算、監査 |

- Publicの主対象はサービス説明または一つの`public_entry_link`であり、公開一覧ではない。
- Homeの主対象は本人の`certificate`と、本人が管理権限を持つ`issuance_program`である。`creator_profile`自体を発行カードとして表示してはならない。
- Studioの主対象はセッションで認可された一つのクリエイターと、その配下の一つの発行プログラム、提供物、集計、収益またはスレッドである。
- Opsの主対象は一つの要対応ケースまたは監査対象である。全運用操作を一画面へ並べない。
- シェル、ナビゲーション、APIはサーバー側の閲覧コンテキストで同じ権限を適用する。
- 所有、Creator管理権限、有効利用権を満たさない詳細・一覧・検索・通知はデータ本体を返さず、存在を示さない。
- メニュー非表示だけで権限を制御しない。
- デスクトップは左サイドバー、ページヘッダー、可変コンテンツ領域を使う。モバイルはシェル専用の下部ナビゲーションを最大4項目まで表示する。
- タップ領域は44px以上、キーボード操作、フォーカス、エラー要約、色以外の状態表示を必須とする。

## Homeのナビゲーションとユーザー導線

Homeのナビゲーションは画面一覧ではなく、認証済み利用者が次に行う目的の順に構成する。プロフィールと設定を日常の記録確認と同列に置かず、Creator管理をアカウント設定の中へ隠さない。

デスクトップのHomeサイドバーは次の階層を固定する。

```text
XXGGLL

ホーム

あなたの記録
  保有XXGGLL
  活動の記録

Creator                         Creator権限がある場合だけ
  Studio

────────────

アカウント
  プロフィール
  設定
```

- `ホーム`は現在の状態、要対応、保有中のXXGGLLへ戻る入口である。
- `あなたの記録`は本人の保有対象と取得・支払・保有・利用区分の履歴を確認するための区画である。表示ラベルは`保有XXGGLL`と`活動の記録`にする。
- `Creator`区画は、セッションにownerまたは許可済みstaffのCreatorアクセスが一つ以上ある場合だけ表示する。`Studio`はアカウント設定のリンクとして表示してはならない。
- `Studio`を開いた後はHomeのサイドバーからCreator用シェルへ切り替え、現在認可されたCreatorの`概要`、`発行・提供物`、`匿名集計`、`収益`だけを表示する。権限のないCreatorをナビゲーション、選択肢、エラー文から推測できる形で露出しない。
- `アカウント`区画には`プロフィール`と`設定`だけを置く。プロフィール・設定をHome本文の主操作として案内しない。
- ナビゲーションの非表示は認可の代わりにならない。各遷移先とAPIは対象所有権・Creator権限をサーバーで再検証する。

モバイルのHome下部ナビゲーションは次の4項目を上限とする。

```text
ホーム | 保有XXGGLL | 活動の記録 | その他
```

- `その他`は開閉式メニューとし、`プロフィール`、`設定`、Creator権限がある場合の`Studio`、サインアウトを表示する。
- モバイル下部ナビゲーションへプロフィール、設定、Studioを個別に追加して5項目以上にしてはならない。
- 下部ナビゲーションと開閉式メニューの各タップ領域は44px以上とする。開閉状態を`aria-expanded`で示し、キーボードで操作できるようにする。

Home本文はナビゲーションの説明を繰り返さず、次の順で読む。

```text
現在の状態
→ 要対応事項（存在する場合）
→ 保有中のXXGGLL
→ Creator権限がある場合だけ、発行中のXXGGLL
```

- 現在の状態には`保有中`と`要確認`だけを表示する。表示する値が2つなのに3列目を予約するレイアウトにしてはならない。
- 活動の記録、利用区分、プロフィール、設定への案内専用セクションをHome本文へ追加しない。これらはサイドナビゲーションから開く。
- Creatorの`発行中のXXGGLL`は、本人がownerとして管理する`issuance_program`単位の状態確認と発行開始のために表示する。これはStudioの管理導線の重複説明ではなく、Home上の現在状態スナップショットである。
- 保有がない場合は、`Creatorから案内された個別リンクを開いてください`と示し、説明用の`/start/fan`だけへ進める。URL入力、公開一覧、検索、推薦、汎用購入操作を置かない。Creator未登録者へ発行区画やCreator登録勧誘を表示しない。

## Public

正規ルート、Public共通ナビゲーション、各画面の状態と遷移は[画面台帳](./screen-catalog.md)の`SC-P01`から`SC-P11`を正本とする。

- トップページは、Fanの応援が消えずに振り返れることと、Creatorがファン全体の輪郭を次の活動判断に使えることを最初に示す。発行No、取得日時、取得時のXフォロワー数、グッズ購入は、その結果を裏づける一件のXXGGLLとして製品表示で示す。ヘッダーは画面台帳のPublic共通ナビゲーションを使い、すべてのPublicページから`/flow`へ1クリックで進めるようにする。
- `/flow`は、Creatorの発行、Fanの個別リンク購入、取得時点の記録、商品コード登録、Fan本人の支払額グラフ・来歴、ユーザーランク判定への反映、Creatorの匿名集計と次の活動判断を一方向の流れで説明する。実在データやPublic APIを使わない。
- Fanは取得したいXXGGLLの個別リンクから直接始める。トップに汎用のFan開始操作を置かず、公開カタログ、検索、クリエイター一覧へは遷移させない。
- Creatorには、XXGGLLを発行して設定・統計を管理する公開入口を示す。登録・ログイン後は共通ホームの発行開始へ遷移する。
- Publicに検索、カテゴリ、クリエイター一覧、関連提供物、無料コンテンツ一覧を置かない。
- 個別リンクは内部検索・サイトマップの対象にせず、推測可能なIDを使わない。
- 個別リンクには対象、価格、残数、取得条件、証票取得が個別役務を発生させないことだけを表示する。
- `publicLinkId`は`public_entry_link`のランダムな生トークンであり、連番、プログラムID、クリエイターIDを使わない。サーバーはハッシュだけを保存し、生トークンをログへ出さない。
- 失効、取消、期限切れ、非公開プログラム、停止中クリエイターの個別リンクは、対象や理由を開示せず同じ`404`応答にする。
- 取得操作は`/sign-in`を経由しても、ログイン、登録、OAuth、メール確認の完了後に同じ`/entry/[publicLinkId]/confirm`へ戻す。継続先は同一Originの許可済みルートだけをサーバー側で受け付ける。
- 取得確認画面は、対象、ランク、価格、手数料、合計、通貨、残数、仮押さえ期限、支払済み期限、次回決済日、停止期限、取消・返金条件、証票取得だけでは個別役務が発生しないことを表示してから、一つの確定操作を受け付ける。

## 共通ホーム

正規ルート、各画面のread model、空・失敗・権限状態は[画面台帳](./screen-catalog.md)の`SC-F01`から`SC-F10`を正本とする。

- 認証済みのすべての利用者は`/home`をホームとする。FanとCreatorでダッシュボードの基礎構造を分けない。両方の役割を持つ利用者には、保有カードと発行カードを同じ画面に表示する。
- Homeに入った利用者が最初に判断するのは「いま何を保有しているか」と「確認が必要なものがあるか」である。Homeの見出し、状態表示、要対応、保有カードはこの順序を崩さない。
- ファンには、現在保有するXXGGLLをカード一覧で表示する。各カードはクリエイター、ランク、証票番号、状態、支払済み期限、次回操作を示し、本人の`/fan/supports/[id]`だけへ遷移する。
- `/home`は「いま保有しているXXGGLLと要対応」を判断する画面であり、全期間の支払額グラフ、ランクの根拠、過去の関係を主表示しない。それらは`/fan/activity`と各証票詳細へ分ける。
- クリエイターには、本人が管理権限を持つ`issuance_program`を一件一枚の発行XXGGLLカードとして表示する。`creator_profile`一件をカード化して複数プログラムの件数だけを要約してはならない。各カードはクリエイター、ランク、公開状態、発行数・上限、要対応、最新の匿名集計を示し、本人が認可された`/studio/[creatorId]/offers/[id]`だけへ遷移する。
- クリエイターには、発行カード一覧の先頭に「XXGGLLを発行」ボタンを表示する。`ランク選択 → 下書きの発行カード作成 → 設定 → 公開`の順で進める。下書きカードは作成直後から設定画面と統計画面の入口を持つが、公開前は外部案内リンク・購入・集計値を公開しない。
- Homeには活動記録へのリンク専用区画を置かない。活動と利用区分は`/fan/activity`で確認し、サイドナビゲーションの`活動の記録`から開く。
- 有料XXGGLLの初回取得は `外部案内の個別リンク → 内容確認 → 条件同意 → 決済/取得確認 → /home` とする。
- カタログは有料XXGGLLを保有する利用者だけに表示し、本人の保有先に紐づく提供物だけを返す。
- 証票一覧は現在・過去に分割しない。各証票を一つの連続記録として表示し、失効・譲渡・終了は時刻と状態を来歴に残す。
- 一件の保有証票詳細は、`現在の状態と次の操作`、`取得時点の記録`、`XXGGLLの連続来歴`、`本人だけの支払・グッズ・応援記録`を区画分けして表示する。前保有者の個人情報と支払内訳は返さない。
- `/fan/activity`は「自分の活動」と「利用区分」を分ける。前者ではCreatorごとの一次取得、継続支援、証票支援、確認済みグッズ購入、返金・取消しを来歴と月別表示で振り返り、後者では現在のユーザーランク、反映済みの実績区分、審査・招待が必要な状態を表示する。金額だけの進捗バー、到達保証、他者順位を表示しない。
- プロフィールは独立した属性共有ページを作らない。アカウント名と出身国・地域は、現在保有するXXGGLLの発行者へ自動開示される。その他の入力済みプロフィールは、ユーザーが一つの共通公開フラグを有効にした場合だけ、現在保有する全XXGGLLの発行者へ開示する。Creatorごと・項目ごとの開示先選択は作らない。
- `/fan/settings`は`T-SettingsOverview`の読み取り中心の画面とし、認証操作は`/fan/settings/security`の`T-SettingsDetail`へ分ける。連絡先メールは現行リリースではマスク値の確認だけとし、メール変更の契約が確定するまで操作を表示しない。`/fan/settings`の責務、表示順、状態、再認証、アカウント閉鎖は[設定画面仕様](./settings.md)を正本とする。プロフィール編集、活動記録、保有XXGGLLの更新、Creator管理を設定画面へ複製しない。
- VIP DMの提供設定、他利用者、請求設定をFanに表示しない。

## Studio

正規ルート、permission別の画面状態、作成・公開・精算の遷移は[画面台帳](./screen-catalog.md)の`SC-S01`から`SC-S09`を正本とする。

- URLの`creatorId`だけで対象を決めず、セッションがownerまたは許可済みstaffとして管理できるCreatorだけを受け付ける。
- 管理できるCreatorが一人だけなら、`/studio`からそのCreatorの概要へ自動で進む。対象選択は複数のCreatorを管理する場合だけ表示する。
- 発行カードの作成は`/home`から開始し、`ランク選択 → 下書き作成 → /studio/[creatorId]/offers/[id]`へ遷移する。設定完了後に公開審査または公開へ進む。
- クリエイターには個人の連絡先、決済情報、他Creatorに関する情報、前保有者の情報を返さない。
- `/studio/[creatorId]`はCreatorの要約と要対応への入口に限定する。発行条件の編集・終了とowner専用の現在保有者確認は`/studio/[creatorId]/offers/[id]`、提供物は`offers`、属性は`audience`、メッセージは`messages`、精算は`revenue`へ分離する。
- `audience`は人数、ランク分布、期間推移、地域分布、支援額帯、継続期間、登録済みグッズの傾向、公開可能な任意プロフィールの匿名集計を表示する。支援者名、匿名識別子、XXGGLLの発行Noによる個人一覧・検索・選別を標準機能にしない。
- 発行プログラム詳細の「現在の保有者」区画は、Creatorのownerだけが読取専用で開ける。各行は、そのプログラムの現在の保有者についてだけ、アカウント名、出身国・地域、当該XXGGLLの取得時の購入額、共通公開フラグが有効なときだけ任意プロフィールを表示する。Creator横断一覧、検索、CSV・外部出力、連絡先、継続支援・証票支援・グッズ購入・他XXGGLLの金額、前保有者は表示しない。各閲覧を監査し、staffにはこの区画を返さない。

## Ops

正規ルート、Ops認証・登録、検索、更新、監査の画面契約は[画面台帳](./screen-catalog.md)の`SC-O01`から`SC-O10`を正本とする。

- admin以外にはOpsの存在を示さない。
- `/ops/sign-in`では登録済みパスキーによる認証開始だけを示す。`/ops/enroll`はRailway運用で発行した一回限りの登録記録、開始ブラウザに束縛した短期Cookie、WebAuthn登録challengeがそろう場合だけ初回・復旧登録を行う。Public、Home、Studioのセッション応答、ナビゲーション、通常認証画面にはadmin権限、Ops導線、credentialの存在を露出しない。
- 有効な専用Opsセッションがない場合は、`/ops/sign-in`、事前認可済み`/ops/enroll`、外形監視専用`GET /ops/health`を除く`/ops`、旧`/admin`、`/api/admin`の全配下を理由を区別しない`404`にする。登録リンク・Cookie・challengeの欠落、メール、パスワード、X OAuth、通常セッション、未登録・失効済みパスキーからはOpsを表示しない。`/ops/health`は画面ではなく、機密情報を返さない監視応答だけとする。
- 管理者は対象ユーザーを一人選び、そのユーザーに表示されるHome、保有XXGGLL、プロフィール、設定状態、Creator管理対象をOps内の読み取り専用ビューで確認できる。ユーザー本人のセッションへ切り替えず、ユーザー向けAPIへ管理者例外を追加しない。
- ユーザー検索一覧では識別に必要な最小情報だけを表示する。連絡先、プロフィール値、保有・支払の詳細は一件詳細を開いた後だけ表示し、誰がどのアカウントを閲覧したか監査記録を残す。
- ユーザービューから購入、返還、更新、同意変更、メッセージ送信、公開、精算その他のユーザー操作を実行できない。
- Creator検索一覧では、Creator名・ID・owner連絡先で一人を特定し、一覧にはランク、状態、発行数、保有者数、要確認件数など比較に必要な最小情報だけを表示する。
- Creator詳細は、概要、発行XXGGLL、匿名集計、収益要約、owner・staffアクセスを区画分けして表示する。Creator本人のセッションや管理権限へ切り替えず、Creator向け更新APIへadmin例外を追加しない。
- Creator詳細から公開、停止、発行、精算、権限変更、メッセージ送信その他のCreator操作を実行できない。個人ファン一覧、未同意属性、Stripe Connected Account ID、銀行口座、本人確認書類、秘密値を表示しない。
- 返金、失効、終了、停止、送金は対象、理由、利用者・クリエイターへの影響、結果を確認して一度だけ実行する。
- 全操作を監査記録する。

## 状態と操作

| 状態 | 表示 | 許可する操作 |
| --- | --- | --- |
| 読み込み中 | 対象と待機中 | 戻る、中断 |
| 空 | データがない理由 | 次の一手を1つ |
| 処理中 | 対象、開始時刻、二重操作防止 | 待機、必要時の中断 |
| 反映待ち | 外部決済またはWebhook確認中 | 再課金しない再確認、問い合わせ |
| 成功 | 結果、記録、次の導線 | 証票、応援状況、管理画面へ移動 |
| 要対応 | 原因、影響、期限、復帰方法 | 再試行、設定変更、問い合わせ |
| 未認証 | 対象データを返さず、認証が必要であること | 検証済み`returnTo`によるログイン、戻る |
| 認可なし・不存在 | 対象と理由を区別しない共通`404` | Homeまたは戻る |

- 決済、証票支援、更新、返還、再発行、出金、返金は、対象・金額・期限・取消条件を確認してから確定する。
- Webhook反映待ちは完了と表示せず、再課金を防ぐ。
- 320px幅から横スクロールなしで主要操作を完結できるようにする。

## 共通の読み順

各画面は、シェル固有の世界観を保ちながらも、`対象 → 現在状態 → 主操作 → 記録・補足`の順に読む。
StudioとOpsの下層で、見出しの直後に説明文、汎用リスト、戻るリンクだけを並べる画面を作らない。

| 画面群 | 最上部 | 中心領域 | 末尾 |
| --- | --- | --- | --- |
| Public開始 | FanまたはCreatorが得る結果 | 4段階以内の開始手順 | 公開範囲・役務境界と開始操作 |
| Fanプロフィール | 発行者への自動開示と任意公開の境界 | 項目保存、共通公開フラグ、現在の発行者プレビュー | 変更履歴 |
| Studio | Creatorと現在位置 | 状態・指標、現在の主要操作 | 対象に紐づく記録とStudio内導線 |
| Ops | 専用HTTPS Originとパスキー再認証が必要であること | 優先キューまたは一件のケース | 監査に必要な識別子と時刻 |

Studioの概要、ファン全体の輪郭、提供物、収益は相互に移動できる導線を持つ。個人情報・秘密値を表示しないという境界説明は一つの区画へまとめ、主要指標と同じ視覚強度で反復しない。

## ルート移行と廃止

次の表は最終構造へ移行するための規範である。旧ルートの画面を残したまま主ナビから隠すだけでは完了としない。

| 現在または旧ルート | 判定 | 正規の移行先 | 完了条件 |
| --- | --- | --- | --- |
| `/creator` | MERGE | 未登録者は`/start/creator`からオンボーディング、登録済み利用者は`/home`または`/studio` | 発行フォーム・管理カードを置かず、全内部リンク移行後に旧画面を廃止する |
| `/studio` | REBUILD | `/studio` | 未登録時はCreator開始、一人を管理する場合は概要へ自動遷移、複数管理時だけCreator選択を表示し、ownerとstaffの権限差をサーバー応答と一致させる |
| `/supporter` | MERGE | `/fan/supports`と`/fan/supports/[id]` | 一覧と詳細を別read model・別画面に分離し、内部リンクと決済復帰先を移行する |
| `/services` | MERGE | `/fan/catalog` | 有効な有料証票に紐づく本人向け提供物だけを返す |
| `/vip-dm` | MERGE | `/fan/messages` | 利用権のある本人のスレッドだけを表示し、公開商品一覧を作らない |
| `/creator/vip-dm` | MERGE | `/studio/[creatorId]/messages` | 対象Creatorの管理権限と`messages_manage` permissionをサーバーで検証する |
| `/creator/vip-invites` | MERGE | `/studio/[creatorId]/messages` | 招待とコンシェルジュを対象スレッドの状態として統合する |
| `/creator/payouts` | MERGE | `/studio/[creatorId]/revenue` | 収益、保留、出金申請、送金状態を対象クリエイター内へ統合する |
| `/free-certificates` | DEPRECATE | なし | UI、API、主要リンクを削除し、恒久的に`404`とする |
| `/paid-certificates` | DEPRECATE | `/entry/[publicLinkId]` | 一覧へは転送せず`404`。個別リンク取得が完成するまで有料取得を機能ゲートで停止する |

## 中心導線

```text
Fan:
外部の個別リンクを開く
→ 対象・条件・役務境界を確認する
→ 認証する
→ 同じ対象の取得確認へ戻る
→ 金額・期限・継続条件へ同意する
→ 予約・決済を一度だけ開始する
→ サーバー確定または反映待ちを確認する
→ Homeで本人の保有状態を確認する
→ 一つの証票詳細で来歴と次の操作を確認する

Creator:
Creator向け開始を選ぶ
→ 認証し、必要な場合だけ公開プロフィールを登録する
→ Homeで「XXGGLLを発行」を選ぶ
→ クリエイターとランクを選ぶ
→ 下書きの発行プログラムを作る
→ 一つの発行カード詳細で条件を設定する
→ 公開審査または公開を確定する
→ 個別リンクを外部で案内する
→ Studioで匿名集計・収益・要対応を確認する

Ops:
専用Ops Originを開く
→ スマートフォン等の登録済みパスキーで利用者検証を完了する
→ 一般利用者と分離した短期OpsセッションでOpsを開く
→ 優先キューから一つのケースを選ぶ
→ 対象・理由・期限・影響・証跡を確認する
→ 必要なら再認証する
→ 一つの許可済み操作を確定する
→ 結果と監査ログを確認する
```
