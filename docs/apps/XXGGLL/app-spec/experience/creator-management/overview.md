# XXGGLL Creator管理

## 1. 目的

Creator管理は、Creator ownerと許可済みstaffが「いま確認すべきこと」を判断し、発行、集計、収益、別契約、権限管理へ迷わず進むための業務画面群である。独立したブランド、SNS、汎用BIダッシュボードにはしない。画面上の名称は「Creator管理」に統一し、旧シェル名は互換URLと既存コードの移行名にだけ残す。

本カテゴリはCreator管理固有の表示順、read model、状態、文言、受け入れ条件を所有する。全画面共通の視覚値は[デザイン仕様](../design.md)、CSSの実装値は[CSS実装仕様](../css.md)、認可の原則は[Identity and Access](../../security/identity-and-access.md)を正本とする。

## 2. 情報構造

Creator管理のサイドメニューは次の順序と名称に固定する。画面ごとに項目名、順序、左端、本文幅を変えない。

| 順序 | 表示名 | 正規ルート | 利用者が解く問い |
| --- | --- | --- | --- |
| 1 | 概要 | `/studio/[creatorId]` | いま最初に確認・対応することは何か |
| 2 | 発行プログラム | `/studio/[creatorId]/programs` | どの発行がどの状態で、次に何が必要か |
| 3 | ファン全体の傾向 | `/studio/[creatorId]/audience` | 現在の保有者全体にどの傾向があるか |
| 4 | 収益・精算 | `/studio/[creatorId]/revenue` | 確認中、精算可能、申請中、送金済みはいくらか |
| 5 | 別契約の提供物 | `/studio/[creatorId]/offerings` | XXGGLLとは別の契約を何件管理しているか |
| 6 | 設定・権限 | `/studio/[creatorId]/settings` | 公開状態、同意、staff権限はどうなっているか |

- `creatorId`を人が読む主識別子として表示しない。Creator名を常時表示し、技術IDは詳細情報へ置く。
- 一つのCreatorだけを管理できる場合、`/studio`はそのCreatorの概要へ直接遷移する。複数の場合だけ選択画面を表示する。
- 対象変更はCreator名の近くに置き、各ページの本文末尾へ旧シェル名の概要リンクや「Homeへ戻る」を反復しない。複数Creatorを管理できる場合はラベル付きのネイティブselectを使い、選択先にも現在ページのpermissionがあれば同じ機能、なければ概要へ移動する。一つだけの場合はselectを表示しない。
- permissionがない項目はサーバーがナビゲーションread modelから除外する。CSSやクライアントfilterだけで隠さない。
- `設定・権限`はownerだけに表示する。staffには概要の対象バーで自分の許可範囲を読取表示する。

## 3. 共通シェル

### 3.1 デスクトップ

幅1024px以上は、全Creator管理画面で次の骨格を共有する。

```text
┌─ 240px ─────────────┬──────────────────────────────────────────────┐
│ XXGGLL              │ Creator名 / 対象変更 / 自分の権限          │
│                     ├──────────────────────────────────────────────┤
│ ホーム              │ ページ名                         主操作      │
│ あなたの記録        │ この画面で判断できること                      │
│                     │                                              │
│ Creator管理         │ 状態・要対応                                  │
│   概要              │ 主データ                                      │
│   発行プログラム    │ 補足・基準時刻                                │
│   ファン全体の傾向  │                                              │
│   収益・精算        │                                              │
│   別契約の提供物    │                                              │
│   設定・権限        │                                              │
│                     │                                              │
│ アカウント          │                                              │
└─────────────────────┴──────────────────────────────────────────────┘
```

| 部位 | 固定値・結果 |
| --- | --- |
| シェル | 左240px、右`minmax(0, 1fr)`の2列。Creator画面だけ別の外側余白を作らない |
| 本文 | 左端はサイドメニュー右端から40px、右余白40px、最大幅960px。全Creatorルートで同じ左端に揃える |
| 上端 | 本文上端32px。対象バー40px以上、下余白24px、その後にページヘッダーを置く |
| ページ名 | 日本語の`h1`一つ、32px / 1.25、800。英字eyebrowや装飾番号を上に重ねない |
| 説明 | 16px / 1.75、最大68文字幅、2文以内。ページ名の言い換えをしない |
| セクション | 前区画との間40px、`h2`は22px / 1.4、本文との間16px |
| 指標 | 28px / 1.2を上限とし、同じ画面に4件まで。64pxの巨大数値を業務画面へ使わない |

主操作がある画面だけ、ページヘッダー右側に一つ置く。集計、概要、権限のないstaff画面では、操作を作るためだけのボタンを置かない。

### 3.2 タブレットとモバイル

| viewport | ナビゲーション | 本文 |
| --- | --- | --- |
| 768px〜1023px | 共通上部ヘッダーの直下にCreator管理の横スクロールしない2行以内のナビを置く。入り切らない場合は「Creator管理メニュー」ボタンで全項目を開く | 左右24px、最大760px、1列 |
| 320px〜767px | 共通ヘッダー + 「概要 / 発行 / 傾向 / その他」の4項目以内。その他に収益、提供物、設定を同じ順序で置く | 左右16px、1列。390pxと320pxで本文横スクロールなし |

モバイルでもDOMの読み順は「対象 → ページ名 → 状態 → 主データ → 補足」とする。デスクトップだけに重要な値を置かず、表を単純に列非表示にしない。

## 4. 共通ページヘッダー

Creator管理の全ページは同じ部品と順序を使う。

1. 対象バー: Creator名、対象変更、ownerまたはstaffの権限要約、データ基準時刻。
2. ページヘッダー: 日本語ページ名、判断できる内容、該当時だけ主操作一つ。
3. 状態領域: 取得失敗、権限変更、反映待ち、要対応。正常時は空にする。
4. 本文: ページ固有の主データ。

ページごとに`context-links`、戻るナビ、英字の`eyebrow`を追加しない。現在地はサイドメニューの選択状態と`aria-current="page"`で示す。

## 5. 認可と応答

| 利用者 | 概要 | 発行 | 傾向 | 収益 | 提供物 | 設定・権限 |
| --- | --- | --- | --- | --- | --- | --- |
| owner | 読取 | 読取・変更 | 匿名集計読取 | 読取・申請 | 読取・変更 | 読取・変更 |
| staff | membershipあり | 一覧・詳細の読取だけ。作成・変更は`programs_manage`導入まで不可 | `audience_read`時だけ | `revenue_read`時だけ。出金申請不可 | `offers_manage`時だけ | 自分の権限要約だけ。画面は不可 |
| その他 | 不可 | 不可 | 不可 | 不可 | 不可 | 不可 |

- 画面、API、サイドメニューは同じmembershipとpermission判定結果を使う。
- 未認証は認証へ進めるが、対象Creatorを応答へ含めない。認可なしと不存在は同じ`404`にする。
- permission失効後の再読込、別タブの更新、確定操作ではサーバーで再照合する。
- owner限定の現在保有者開示は[発行プログラム](./programs.md)にだけ置き、概要と傾向には個人行を返さない。

## 6. 旧実装からの移行契約

| 旧表示・ルート | 問題 | 正規化 |
| --- | --- | --- |
| 旧Creator管理ラベル、旧概要ラベル | 製品概念と技術URLが混在 | UIは`Creator管理`、`概要`へ統一 |
| `/studio/[creatorId]/offers` | 別契約の提供物と発行プログラム詳細で親子の意味が異なる | 発行は`/programs`、別契約は`/offerings`へ分離 |
| `/studio/[creatorId]/offers/[programId]` | 親が提供物、子が発行プログラム | `/studio/[creatorId]/programs/[programId]`へ移行 |
| `/studio/start` | Creator管理シェル内に登録導線が分裂 | `/start/creator`へ統合し、登録済みは対象Creatorの概要へ進む |
| Audienceから`/api/creator/support-expressions`を取得 | 集計と個人応援文が同じ画面・失敗状態に混在 | Audienceから呼出しを削除し、契約メッセージの機能gateへ分離 |
| 各ページ固有の`context-links` | 順序、左端、戻る位置が画面ごとに変わる | 共通サイドメニューと対象バーへ集約 |
| 英字eyebrow + 巨大見出し | 日本語の業務名より装飾が先に読まれる | 業務画面の英字eyebrowを廃止し、32pxの日本語`h1`へ統一 |

旧ルートは内部リンクと復帰先から先に除去する。移行期間だけ、`GET`と`HEAD`について認証・認可を旧ルートで確認してから同一Creator内の正規ルートへ`307`で転送する。mutationやAPIを転送しない。認可なし・不存在を転送先の差で識別できないようにし、本番公開後14日間、旧ルートへの正規内部流入0件を確認してから`404`へ切り替える。

## 7. 共通受け入れ条件

- 1440pxで全Creator画面の対象バー、`h1`、最初の本文区画の左端がそれぞれ一致する。
- 1024px、768px、390px、320pxでナビゲーション項目の順序が変わらず、本文または画面全体に意図しない横スクロールがない。
- ページ名、主操作、空状態、エラー状態が英語や内部状態値だけで表示されない。
- permissionのない項目がナビゲーション、HTML、RSC payload、API応答、prefetch結果へ含まれない。
- 全ルートで対象Creatorを変更しても、前のCreatorの値、リンク、cacheが残らない。
- 読み込み失敗を0件・0円・傾向なしに置き換えない。

## 9. Review response

対象はCreator管理の共通シェル、概要、発行、Audience、収益、別契約、設定、画面台帳、要件、データモデル、コントロール、属性開示である。2026-08-16の現行実装との差分も、正しい根拠ではなく移行対象として確認した。

初回判定は`Revise`、P1修正後の再レビュー判定は`No material findings`とする。

| 重要度 | 初回指摘 | 応答 |
| --- | --- | --- |
| P1 | Audienceで生件数を禁止しながらワイヤーとcoverageに正確な人数が残り、時系列差分の推測対策もなかった | 件数・割合を5単位へ丸め、週次snapshot、補完抑制、1〜4人の時系列差分抑制、内部セルと公開payloadのDB権限分離を追加した |
| P1 | グッズ傾向が固定大分類を要求する一方、保存モデルは自由な`product_label`だけで実装不能だった | 正規販売元が確定する8分類の`product_category`、未定義拒否、旧行の決定的移行・隔離・release gateを追加した |
| P1 | staffの発行変更可否が未定義で、旧routeの`308`がmutationまで恒久転送する余地があった | `programs_manage`導入まではstaff読取・owner変更に固定し、旧画面は認可済み`GET` / `HEAD`だけを14日間`307`、mutationは転送しない契約にした |
| P1 | Ops Creatorビューが現行の非抑制集計を独自に返せる余地があった | Creator画面と同じ`RM-CreatorAudienceV1`の公開snapshotだけを返し、Ops用の非抑制queryを禁止した |
| P2 | 丸め規則と週次jobの資格情報境界が実装者任せだった | 端数規則、Cron専用DB role、Web / Opsの抑制済みview限定を明記した |

再レビューでは、0・1・4・5・6人、週次差分、複数保有、譲渡・再取得、前保有者支払、返金帰属不明、共有無効、旧グッズ行、owner / staff / Ops、旧route、source失敗を確認した。P0/P1の未解決指摘はない。
